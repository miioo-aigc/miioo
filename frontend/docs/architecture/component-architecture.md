# 组件架构规范

> 文档类型：前端组件分层与复用规则
> 最后更新：2026-07-15
> 适用范围：`src/components/`、`src/pages/`、`src/hooks/`、`src/stores/`、`src/api/`

## 1. 目标

组件拆分的目标不是把文件切得越碎越好，而是让每个文件只有一个清晰职责，让页面入口能够看懂页面结构，让重复能力拥有稳定的公开接口。

所有迁移以“结构变化、行为不变”为前提。除非另有需求说明，同一次迁移不得同时修改接口协议、业务规则、视觉稿和用户流程。

## 2. 目录分层

```text
src/components/
├── ui/          无业务基础 UI：Button、Input、Select、Tabs、Tooltip、Loading
├── feedback/    跨页面反馈：Toast、EmptyState、ErrorState、LoadingState
├── overlay/     跨页面容器：Modal、Drawer、Popover、ConfirmDialog
├── actions/     跨业务动作：保存、删除、生成、上传等带业务语义的组件
├── project/     项目域组件
├── creation/    创作域组件
├── storyboard/  分镜域组件
├── assets/      资产域组件
├── subject/     主体域组件（当前代码目录）
└── script/      剧本域组件
```

目录按复用范围表达职责，不要求为了目录整齐立即搬动所有历史文件。新增文件必须按下列规则归类；历史文件在实际迁移时逐步调整。

## 3. 放置决策

### 3.1 `components/ui/`

适用于只负责视觉、通用交互和可访问性的基础组件，例如 `Button`、`IconButton`、`Input`、`Select`、`Tabs`。

必须满足：

- 不知道项目业务名词、业务 API、业务 Store、页面路由和业务 Toast 文案。
- 通过 props 接收值、状态、标签、图标和回调，不直接读取页面状态。
- 优先使用设计 Token；支持默认、悬停、按下、禁用、加载、聚焦等通用状态。
- 不为某一个页面添加无法解释的业务分支。

如果组件需要调用 API、判断权限、弹出业务提示或组装业务参数，不得放入 `ui/`。

### 3.2 `components/feedback/` 与 `components/overlay/`

`feedback/` 负责跨业务的提示和状态展示，`overlay/` 负责跨业务的遮罩与容器。它们可以接收业务方传入的标题、内容、状态和回调，但不直接拥有具体项目请求。

确认删除项目、生成主体等带业务语义的内容，可以由页面或业务域组件调用通用 `ConfirmDialog`，业务请求仍留在页面、Hook 或动作组件。

### 3.3 `components/actions/`

适用于跨页面复用、但含有保存、删除、生成、上传、权限或 Toast 等业务语义的动作。动作组件可以调用 API 或 Hook，但必须通过明确 props 暴露输入和回调，不得把整个页面状态对象无差别透传进去。

如果动作只属于一个业务域，优先放入对应业务域目录，不为了“看起来通用”提前放入 `actions/`。

### 3.4 `components/<domain>/`

适用于同一业务域内稳定复用的卡片、列表、编辑区、工具栏、选择器和结果展示。业务域组件可以组合 `ui`、`feedback`、`overlay`，并在职责明确时使用业务 API、Hook 或 Store。

业务域组件不得反向引用页面入口；它不能通过隐式闭包依赖页面局部变量，所有依赖必须体现在 props、Hook 或明确的业务工具参数中。

### 3.5 页面内局部组件

页面内定义组件只适用于：

- 只出现一次；
- 强依赖当前页面上下文；
- 当前还没有稳定复用契约。

一旦出现第二处复用、职责稳定，或局部组件已经遮蔽页面入口结构，就必须评估迁移到业务域目录。不得为了单纯降低行数强行抽象，也不得继续复制已有基础组件的视觉实现。

## 4. 组件接口规则

- props 只传组件真正需要的字段；优先传清晰的值和回调，不传整个 `pageState`。
- 回调名称使用事件语义，例如 `onChange`、`onConfirm`、`onDelete`；参数结构保持稳定并在迁移记录中写明。
- 组件需要多个相关字段时，可以使用一个明确命名的配置对象，但不要把页面所有状态打包透传。
- API 返回字段的兼容转换放在 API 适配工具或业务域纯函数，不散落在多处 JSX 中。
- 组件拆分后必须逐项检查 props、回调、闭包变量、默认值、导出方式和调用方。

## 5. 规模警告线

以下是维护提醒线，不是绝对硬限制，也不允许通过压缩代码、删除空格或牺牲可读性规避。超过提示线先盘点职责；达到强提醒线必须做结构审计，只有明确违反职责边界时才阻断：

| 文件类型 | 提示线 | 强提醒线 | 达到强提醒线后的动作 |
|---|---:|---:|---|
| 页面入口 | 600 行 | 900 行 | 审计是否混入大量稳定 UI、重复业务区块或多个未分层流程 |
| 通用 UI 组件 | 300 行 | 500 行 | 审计是否混入业务 API、Store、页面依赖或业务域组件 |
| 业务区块组件 | 500 行 | 800 行 | 审计独立区块以及展示、交互和动作边界 |
| Hook | 350 行 | 500 行 | 审计状态域、数据适配、副作用和页面闭包依赖 |
| 单个函数 | 50 行 | 不设强提醒线 | 检查是否混合请求、转换、状态和渲染职责 |

复杂历史页面可以暂时超过强提醒线，但必须记录当前迁移状态和原因。新建页面不应以超长文件作为默认方案。

## 6. 完成标准

组件迁移完成前必须确认：

1. 组件职责和目录层级明确。
2. import/export 与调用方完全对应。
3. 全局搜索不存在旧组件名、失效回调或未定义引用。
4. 文件顶部结构索引已同步（适用时）。
5. `npm run build`、`npm run check:architecture` 和相关定向检查通过。
6. 关键交互、接口参数和视觉状态与迁移前一致。
