# 分集剪辑进度跨设备同步：后端实施契约

日期：2026-10-30。状态：前端已按本文预接线，后端待实现与联调，尚未跨设备验收。

**本文替代此前“项目级解锁集合”方案。用户已确认按分集推进，不能一集解锁导致整项目所有分集进入剪辑。** 不修改当前已部署的 openapi.json 来伪装接口存在；后端实现后须同步正式契约。

## 1. 产品规则与状态定义

- 第一集点击“开始剪辑 → 在线剪辑”，仅第一集保存为 editing，卡片显示“剪辑中”。
- 第二集已分镜但没有进入剪辑，仍为 storyboarded，卡片显示“已分镜”，不能在剪辑页直接切入第二集。应从第二集分镜页单独开始剪辑。
- 项目顶部剪辑导航：任意一集为 editing 或 edited 即可用；剪辑页分集选择器只提供已解锁分集。
- 卡片状态：draft/scripted/extracted → 未分镜；storyboarded → 已分镜；editing → 剪辑中；edited → 完成。legacy generated/videos_ready 仅表示视频/分镜产物，不得推断为已进入剪辑。
- 前端内部 generated 是旧卡片展示键，当前将服务器 editing 映射到该展示键；后端不要因此返回 generated 代表剪辑。
- 同一项目在另一电脑重新打开或刷新后读取最新状态。不要求已打开页面实时更新，不同步用户当前停留页面。
- 本次只新增进入剪辑的状态推进。完成判定沿用后端已有业务规则；不能把进入、建草稿或单次导出自动定义为完成。重复进入已完成分集保持 edited。

## 2. 已定接口（前端已调用，后端新增）

POST /api/projects/{project_id}/episodes/{episode_id}/start-edit

鉴权：现有登录鉴权。请求 Content-Type: application/json，正文 {}。

成功：HTTP 200，返回完整 EpisodeResponse，并增加必需 project_id；不包裹 data 或 episode。示例：

~~~json
{
  "id": "episode-1",
  "project_id": "project-a",
  "title": "第一集",
  "episode_number": 1,
  "content": "保留原正文",
  "summary": "保留原摘要",
  "status": "editing",
  "created_at": "2026-10-30T01:00:00Z",
  "updated_at": "2026-10-30T02:00:00Z"
}
~~~

前端检查 id、project_id 与请求一致，且 status 必须为 editing/edited；不符合即视为未确认，不跳转。

### 服务端事务规则

1. 验证用户有项目编辑权限，分集确实属于路径中的项目。
2. 验证已分镜前置条件；仅当前分集可以推进。未达到条件返回 409，并给出可读提示。
3. 原子、幂等地推进 storyboarded → editing；已经 editing 原样返回；已经 edited 保持完成。重复请求或网络重试不创建重复任务/工程、不降级。
4. 此接口只保存状态，不创建草稿。前端确认成功后沿用现有 prepareOnlineEditing：有草稿进入列表，无草稿创建后进入编辑器。
5. 状态保存成功而草稿创建失败：保留 editing，提示进入失败，可重试；不得回滚成 storyboarded。
6. 同分集并发推进/导出/分镜任务完成回调必须保护 editing/edited，不被晚到的 storyboarded 覆盖。修改普通剧本文字也不能悄悄降低进度。
7. 401 未登录；403 无编辑权限；404 项目/分集不存在或不匹配（按现有隐藏资源规则）；409 前置条件不满足；422 参数错误；5xx 写入失败。沿用现有错误体 code/message/detail。

## 3. 现有读取接口需要补齐

- GET /api/projects/{project_id}/episodes：每集返回持久化 status，新增 editing/edited；其他字段和列表结构保持现有兼容。
- GET /api/projects/{project_id}/overview：episode_progress 按 episode_id 返回对应状态；与 episodes 同源，不再仅依据视频数量计算后覆盖 editing/edited。
- POST 返回成功后，上述 GET 必须读到已提交结果；后端及网关缓存应失效，不能返回旧 storyboarded。
- 通用分集 PATCH 的状态白名单和序列化类型应识别新增状态，但进入剪辑的业务推进使用上述专用接口，不允许普通 PATCH 绕过权限/前置校验或降级。
- 不需要新增项目级 unlocked_steps，不占用项目 status/notes/description。

## 4. 访问边界与历史数据

- 前端只向剪辑页传入 editing/edited 分集；手工访问未解锁分集或缺少分集参数的编辑器链接会被拦截。前端提示不是服务端权限边界。
- 后端创建/修改/渲染工程必须校验项目、分集与工程归属。已知 comp_id 不得读取或操作另一项目/分集的工程。业务写入应要求该集已解锁。
- 上线迁移按真实工程的 episode_id 将已有剪辑工程对应分集补为 editing，已完成保持 edited。工程缺失或分集归属异常应记录待核对，不推及其他集。
- 旧 localStorage 只有项目级 edit，无法证明哪一集进入剪辑；前端已停止用它解锁，不会自动把全部集上传为 editing。没有工程或其他可信分集记录时，用户重新从目标分集点击开始剪辑即可幂等补记。
- 删除草稿不自动撤销 editing；工作流重置不在本任务内。
- 导出剪映包不等于进入在线剪辑，本次不通过该动作推进 editing。

## 6. 联调验收清单

1. A 项目至少三集：第一、二集已分镜，第三集未分镜。
2. A 电脑仅第一集开始在线剪辑：第一集 editing，第二集 storyboarded，第三集保持原状态。
3. B 无缓存打开、带旧缓存刷新、重新登录打开，均得到相同三集状态。
4. B 剪辑分集选择器只出现第一集；第二集手工链接不得操作，需从第二集分镜单独开始剪辑。
5. 第一集无草稿和已有草稿两条路径均成功；写失败不建草稿、不跳转；写成功而建草稿失败可重试且不倒退。
6. 重复点击、网络重试、两电脑并发推进、完成回调与分镜回调乱序，不重复建状态、不降级、不影响其他集。
7. 保存期间切换账号/项目，不把晚到结果写入新页面。
8. 已完成保持完成；视频生成完成不能被误标为剪辑中。
9. 历史工程按真实分集迁移；没有分集证据的旧本地标记不批量解锁。
10. 验证 403/404/409/5xx 错误体，以及 episodes、overview 和 start-edit 三接口的一致性。
