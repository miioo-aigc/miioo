# 主体图片资产重复问题修复需求

> 文档用途：交接后端排查并修复主体页面图片资产重复问题。
>
> 问题范围：生产环境「主体页面」以及「资产库 - 项目资产」中，同一主体下出现疑似重复的图片资产。
>
> 发现日期：2026-08-04

## 一、问题背景

生产环境中，主体页面接口和项目资产接口均返回了同一主体下的多条图片资产。当前观察到的现象是：页面上看起来出现重复图片，且这些图片已经以多条独立资产记录进入后端返回结果。

本次重点样本为主体「小女孩」：

```text
subject_id = bed9b868-2cea-4de7-af71-034b803a39c4
project_id = dd2fc526-f8b8-46ef-bce6-e54dbb84ca1a
```

主体接口返回：

```text
GET /api/subjects?type=character
```

其中「小女孩」返回：

```json
{
  "id": "bed9b868-2cea-4de7-af71-034b803a39c4",
  "name": "小女孩",
  "image_count": 4,
  "primary_asset_id": "643d2976-aa0c-4993-9d68-1b7ae5d229a4"
}
```

项目资产接口返回：

```text
GET /api/assets?project_id=dd2fc526-f8b8-46ef-bce6-e54dbb84ca1a
```

返回了该主体的 4 条图片资产：

| 资产 ID | `subject_id` | `is_primary` | `created_at` |
| --- | --- | --- | --- |
| `aa952f3f-5d1f-4c35-9b96-f9fe5f04b5b4` | `bed9b868-2cea-4de7-af71-034b803a39c4` | `false` | `2026-08-04T10:26:28.534197` |
| `643d2976-aa0c-4993-9d68-1b7ae5d229a4` | `bed9b868-2cea-4de7-af71-034b803a39c4` | `true` | `2026-08-04T10:24:42.499065` |
| `16932712-3548-4f7e-b1a6-2ecd4fd6027c` | `bed9b868-2cea-4de7-af71-034b803a39c4` | `false` | `2026-08-04T10:09:53.493674` |
| `4ac7ead1-6af2-4b72-8f6d-5a8a41f348f7` | `bed9b868-2cea-4de7-af71-034b803a39c4` | `false` | `2026-08-04T10:09:11.260040` |

这 4 条资产的 `id`、`file_url`、`preview_url` 均不同，但创建时间明显形成两次创作批次：

```text
第一批：2026-08-04 10:09:11、2026-08-04 10:09:53
第二批：2026-08-04 10:24:42、2026-08-04 10:26:28
```

因此需要后端确认：这是两次创作各产生两张合法候选图，还是每次创作结果被重复落库两次。

## 二、已确认事实

### 2.1 重复数据已经进入后端响应

当前不是单纯的前端数组重复追加，原因如下：

1. `assets` 接口返回了多条独立记录。
2. 每条记录有不同的资产 `id`。
3. 每条记录有不同的原图路径和预览路径。
4. `subjects.image_count` 同步返回了对应数量。
5. 前端没有能力凭页面展示结果解释为什么数据库中已经存在多条资产记录。

因此，即使前端增加展示层去重，也只能隐藏重复卡片，不能修复重复资产已经落库、数量统计错误、分页数量错误以及删除语义错误等问题。

### 2.2 不能仅按主体名称或 `subject_id` 去重

同一主体拥有多张候选图是合法业务。例如：

```text
同一 subject_id
  -> 多张候选图
  -> 其中一张 is_primary = true
```

不能因为多条记录的 `name`、`subject_id` 或提示词相同，就把它们全部合并成一张。

本次需要识别的是：

```text
同一主体
  + 同一次生成任务
  + 同一个生成结果
  -> 被重复写入多条资产记录
```

只有确认两条记录属于同一个生成结果，才能合并、废弃或隐藏其中一条。

### 2.3 与此前创作页面重复问题的关系

两类问题属于同一大类：后端把同一业务结果对应的多条资产记录返回给前端；但目前没有证据表明它们是同一个具体来源：

此前创作页面的重复关系是：

```text
creation_shot_image
creation_shot_import
```

本次主体资产响应中暂未看到：

```text
source
task_id
generation_id
derived_from_asset_id
origin_url
```

所以不能直接把主体资产重复归因于 `creation_shot_import`。请后端单独核查主体图片生成和主体资产写入链路。

## 三、需要后端定位的根因

请以后端数据库和生成任务日志为准，确认以下哪一种情况实际发生：

### 情况 A：一次生成任务写入了两条资产记录

可能链路：

```text
主体图片生成任务完成
  -> 保存主体图片记录
  -> 保存项目资产记录
  -> 同一个结果再次触发保存
  -> 产生第二条业务资产
```

如果两条记录的文件内容哈希相同，或者一条记录的原图与另一条记录的原图完全相同，则应按重复写入处理。

### 情况 B：一次生成任务合法产生两张候选图，但接口误认为一张

如果一次任务的 `image_count` 或请求参数本来允许生成 2 张图片，那么两条记录可能是合法的不同候选图。此时不能删除其中一条，应确保：

```text
每个生成结果有独立的结果序号或结果 ID；
每张候选图只落库一次；
主体的 image_count 等于实际合法候选图数量；
只有用户选择的那张设置 is_primary = true。
```

### 情况 C：主体图片表和项目资产表被当成两张业务图片返回

如果主体图片表和项目资产表各保存一条记录，但两条记录指向同一个物理文件或同一个生成结果，则这不是两张候选图，而是同一业务资产的两个存储/关联记录。

此时应统一资产模型：

```text
一张图片对应一个稳定的业务 asset_id
主体与资产通过关联关系连接
主体候选列表和项目资产列表不要各自再创建一条图片资产
```

### 情况 D：生成回调、重试或前端重复提交没有幂等

请排查：

1. 生成请求是否有相同的 `task_id`、`request_id` 或幂等键。
2. 任务回调是否可能重复执行保存逻辑。
3. 任务重试时是否重新创建资产，而不是复用已有结果。
4. 前端轮询或刷新是否会触发重复保存接口。
5. 生成成功后是否同时由任务回调和查询接口写入资产。
6. 同一个结果是否存在多个异步消费者同时落库。

## 四、后端修改需求

### 4.1 增加生成结果与资产的稳定关联

主体图片资产接口至少应返回以下字段，或提供等价字段：

```json
{
  "id": "资产记录 ID",
  "asset_id": "稳定业务资产 ID",
  "subject_id": "主体 ID",
  "source": "subject_generated",
  "task_id": "生成任务 ID",
  "generation_id": "单次生成结果 ID",
  "result_index": 1,
  "content_hash": "文件内容哈希",
  "is_primary": false,
  "created_at": "2026-08-04T10:24:42.499065"
}
```

字段要求：

- `task_id` 标识一次生成任务；
- `generation_id` 标识任务中的一个独立结果；
- `result_index` 标识同一任务生成的第几张图；
- `content_hash` 用于识别完全相同的物理文件；
- `source` 区分主体生成、用户上传、分镜导入等来源；
- 不能仅依赖图片 URL、名称或提示词推断资产身份。

如果当前数据库已有等价字段，请在接口中返回，不需要重复新增字段。

### 4.2 保存流程必须幂等

对同一个生成结果，后端必须保证重复回调、重复请求和任务重试不会重复创建业务资产。

建议使用以下组合建立唯一性约束或幂等查询：

```text
source + task_id + generation_id
```

如果没有 `generation_id`，至少使用：

```text
source + task_id + result_index
```

对于无法提供任务 ID 的历史上传流程，应由后端生成并持久化唯一的 `request_id` 或内容哈希，不能使用名称和时间作为唯一键。

要求：

1. 重复保存返回已存在的资产，而不是创建新资产。
2. 并发保存时使用数据库唯一约束或事务锁，不能只依赖应用层先查后写。
3. 任务重试不产生第二个 `asset_id`。
4. 查询接口不会因为同一任务有多条保存记录而返回重复业务结果。

### 4.3 修复主体资产查询接口

请检查：

```text
GET /api/subjects?type=character
GET /api/assets?project_id={project_id}
```

要求：

1. `subjects.image_count` 只统计合法的主体候选图片，不统计重复记录、软删除记录和参考图记录。
2. `subjects.primary_asset_id` 必须指向当前主体真实存在且属于该主体的资产。
3. `assets` 接口不能把同一生成结果的重复落库记录作为多张独立图片返回。
4. 分页时应先按业务资产去重，再计算 `total`、`has_more` 和返回列表。
5. `is_primary` 只表示定稿状态，不得用来判断一条记录是否重复。
6. 参考图、分镜导入副本和主体候选图必须通过 `source` 或独立关系区分。

### 4.4 历史重复数据处理

请先提供重复数据诊断结果，再执行数据修复。不能按主体名称、主体 ID 或创建时间直接批量删除。

建议诊断步骤：

1. 查询所有主体图片资产的 `task_id`、`generation_id`、`source`、原图路径和文件哈希。
2. 按 `generation_id` 或等价稳定结果 ID 分组。
3. 对没有任务关联的记录计算原图内容哈希。
4. 确认每组中哪一条是主记录，哪一条是重复记录。
5. 检查重复记录是否被分镜、参考图或其他业务引用。
6. 保留被引用关系完整、创建时间和元数据正确的主记录。
7. 重复记录优先软删除或标记为派生/重复，不要直接物理删除。
8. 修复主体的 `image_count`、`primary_asset_id` 和关联关系。

建议保留规则：

```text
优先保留有稳定 asset_id、task_id、完整元数据且被业务引用的记录；
如果只有一条 is_primary = true，不能仅因为另一条 is_primary = false 就认定另一条重复；
如果两条内容相同，保留一条主资产，其他记录迁移引用后再软删除。
```

## 五、接口响应契约建议

### 5.1 主体列表

主体列表中的图片统计建议明确为：

```json
{
  "id": "主体 ID",
  "image_count": 2,
  "primary_asset_id": "当前定稿资产 ID",
  "primary_image_url": "/uploads/.../primary.png"
}
```

其中：

- `image_count` 是去重后的有效候选图数量；
- `primary_asset_id` 是有效资产 ID，不是主体图片表的临时 ID；
- 被标记为参考图、分镜导入副本或重复记录的资产不计入候选图数量。

### 5.2 主体资产列表

每张图片建议返回：

```json
{
  "id": "资产记录 ID",
  "asset_id": "稳定业务资产 ID",
  "subject_id": "主体 ID",
  "source": "subject_generated",
  "task_id": "任务 ID",
  "generation_id": "结果 ID",
  "result_index": 1,
  "content_hash": "文件哈希",
  "is_primary": true,
  "file_url": "/uploads/.../image.png",
  "preview_url": "/uploads/.../preview.avif"
}
```

如果接口暂时不能返回 `content_hash`，至少必须返回生成任务和结果的稳定关联字段，供前端和后端排查重复。

## 六、前端配合范围

本问题的主修复责任在后端，因为重复记录已经进入接口响应并影响 `image_count`。后端完成幂等保存和查询修复后，前端原则上不需要做全局重构。

前端可以配合：

1. 按 `asset_id`、`id` 和图片 URL 做展示层基础去重。
2. 识别后端新增的 `source`、`generation_id` 和重复标记字段。
3. 在联调期间打印或上报同一主体下的重复资产诊断信息。
4. 补充两次生成、刷新页面、分页加载和任务重试的回归测试。

前端不负责：

1. 根据主体名称、提示词或时间猜测重复资产。
2. 直接删除后端数据库中的任意一条资产。
3. 用 `is_primary` 判断是否重复。
4. 将主体候选图、主体参考图和分镜导入图混为同一类资产。

## 七、验收标准

### 7.1 新生成流程

1. 主体生成一张图片后，数据库只产生一条对应的业务资产记录。
2. 生成回调重复执行时，不新增第二个 `asset_id`。
3. 任务失败重试后，不产生重复资产。
4. 主体接口和资产接口均只返回一条该生成结果。
5. `image_count` 与去重后的有效候选图数量一致。

### 7.2 多张合法候选图

1. 如果请求明确生成多张图片，每张图片有独立的 `generation_id` 或 `result_index`。
2. 不同结果不会被错误合并。
3. 同一结果不会因为重复回调被保存多次。
4. 同一主体可以保留多张候选图，但最多只能有一张有效 `is_primary = true` 定稿图。

### 7.3 历史数据

1. 对「小女孩」样本完成诊断，明确 4 条记录分别属于哪两次任务、每次任务实际产生几张结果。
2. 若确认每批中的一条是重复记录，修复后主体接口 `image_count` 与资产接口数量一致且不再多算。
3. 修复后刷新、重新登录、切换主体和重新打开资产库，重复图片不再出现。
4. 不误删合法候选图、定稿图、参考图源资产或分镜引用资产。
5. 旧资产被引用时，清理重复记录不会破坏主体、分镜和参考图功能。

### 7.4 关联关系

1. 主体 A 的图片被主体 B 当作参考图时，不修改原资产的 `subject_id`。
2. 不修改原资产的 `is_primary`。
3. 删除主体 B 时，只解除 B 的参考图关系，不删除主体 A 的源资产。
4. 分镜导入类副本不作为主体候选图或图片创作结果重复返回。

请针对本次样本明确回复：

1. `aa952...`、`643d...`、`169327...`、`4ac7...` 分别对应哪两个生成任务？
2. 每个任务实际请求生成几张图片？
3. 每条资产对应的 `task_id`、`generation_id`、`result_index`、`source` 是什么？
4. 四张原图的内容哈希是否有相同项？
5. 是否存在主体图片表与项目资产表重复写入同一结果？
6. 是否存在任务回调重复执行、重试不幂等或重复提交？
7. `image_count` 的统计 SQL 是否包含重复、软删除、参考图或导入副本？
8. `GET /api/assets?project_id=...` 是否在数据库层完成业务资产去重后再分页？
9. 历史重复记录准备如何标记、迁移引用和清理？
10. 修复后如何保证同一生成结果不会再次产生多个业务资产？

## 九、推荐落地顺序

### 第一阶段：确认样本并止血

1. 查询「小女孩」4 条记录的任务关联、来源和文件哈希。
2. 判断两次创作各自是生成一张还是两张结果。
3. 临时修正主体和资产查询的统计口径，避免重复记录继续作为有效候选图计数。

### 第二阶段：修复保存幂等

1. 为生成结果补齐稳定关联字段。
2. 对生成回调、重试和重复请求增加数据库级幂等约束。
3. 确保一个生成结果只对应一个业务 `asset_id`。

### 第三阶段：治理历史数据

1. 按稳定结果 ID或文件哈希识别历史重复记录。
2. 检查并迁移主体、参考图、分镜等引用关系。
3. 软删除或标记重复记录。
4. 重新校正 `image_count`、`primary_asset_id` 和列表分页统计。

## 十、最终结论

当前主体资产重复已经不是单纯的前端展示问题。后端接口返回了多条独立资产记录，主体接口也将这些记录计入 `image_count`。时间上形成两次创作批次，强烈提示需要排查生成结果保存流程，但在拿到任务关联和文件哈希前，不能直接删除其中任何一条。

本次后端修复目标是：

```text
一次生成结果只落库一个业务资产；
多张合法结果保留独立结果身份；
重复回调和重试必须幂等；
主体与资产接口按有效业务资产统计和返回；
参考图、分镜导入副本与主体候选图保持独立关系。
```
