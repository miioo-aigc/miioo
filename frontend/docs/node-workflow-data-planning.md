# 节点式工作流：前端工程、数据与生成管理规划

## 一、核心结论

**画布展示当前成果，资产库保留旧成果，生成记录解释每个成果是怎么来的；下游运行时取最新成果，提交后固定本次输入。**

首期不必额外建设节点历史面板，也不需要每次生成都新增结果节点。数据职责需要分开，但不强制拆成三个独立状态仓库。

工程原则：**React Flow 负责画布交互，工作流模型表达业务，编辑操作改变文档，执行协调提交运行，后端保证持久化、权限和任务一致性。** 首期把这些边界做清楚，不提前建设通用流程引擎。

## 二、已确认的产品行为

| 场景 | 预期行为 |
| --- | --- |
| 首期生成方式 | 用户手动触发各个节点 |
| 同一节点再次生成成功 | 新结果替换节点当前展示的旧结果 |
| 旧结果保存 | 数据库中保留，并在资产库中可查找 |
| 查看旧结果生成参数 | 从对应资产的创作详情查看 |
| 上游产生新结果 | 下游下一次生成默认使用新结果 |
| 画布库 | 已决定使用 React Flow，不再进行画布库选型 |
| 后端协作 | 后端同步支持工作流持久化和任务协议建设 |
| 节点生成 | 用户在节点触发生成，不自动执行下游；是否补跑上游仍待约定 |
| 全局生成 | 可以预留用户主动触发整条流程的能力，不等于首期已承诺实现 |
| 未来智能体 | 主要辅助搭建工作流、使用模板；具体能力后续规划，不允许发起扣费生成 |

“替换节点展示”不是删除旧资产，也不是修改旧资产的创作参数。资产库展示与数据库保存可以基于同一条资产记录，不要求重复存储两份。

智能体编辑与付费执行必须分权。创建节点、修改参数、连线或加载模板不得间接触发扣费；服务端应落实执行授权，不能只靠隐藏按钮或提示词约束。模板、全局执行和智能体编辑都不能绕过业务校验。

## 三、运行记录有什么意义

运行记录可以理解为每次生成的独立任务单，记录：

- 哪个工作流、哪个节点发起了生成。
- 提交时实际使用的提示词、模型配置和输入素材。
- 对应的后端任务编号、执行状态与失败原因。
- 成功后产生了哪些资产。

它不是要求新增一个历史记录界面，而是支撑任务恢复、结果归属、创作详情和错误处理的数据。

### 示例：上游更新与下游生成

1. 图片节点生成“海边的房子”，得到图片甲。
2. 视频节点使用图片甲提交生成。
3. 用户修改图片节点参数，生成“山里的房子”，得到图片乙。
4. 图片节点当前展示切换为图片乙。
5. 已提交的视频任务仍然使用图片甲，不受后续修改影响。
6. 用户下一次运行视频节点时，默认使用图片乙。

因此必须区分：**节点现在的参数与输出**，以及**某次任务实际提交的输入**。

单次运行的输入快照不等于整个工作流的历史版本。本规划不包含恢复某个历史时刻的整张画布。

## 四、前端具体怎样分开数据

继续使用项目已有的 Zustand 即可。首先按职责划分数据，再根据实现规模决定放在一个仓库的不同区域，还是拆成独立仓库。

| 数据区域 | 保存内容 | 典型更新时机 |
| --- | --- | --- |
| 工作流数据 | 节点、参数、连线、节点位置、当前输出资产编号 | 修改参数、连接节点、拖动结束、生成成功 |
| 编辑器状态 | 选中节点、缩放、视口、菜单、拖动状态 | 用户操作画布 |
| 运行状态 | 本次输入快照、任务编号、进度、错误、输出资产编号 | 提交任务、收到进度或结果 |

### 1. 工作流数据：现在准备做什么

例如，一个图片生成节点保存当前提示词、模型、位置及当前展示的资产编号。用户将提示词从“海边的房子”改成“山里的房子”时，只修改节点当前参数，不改写旧生成记录。

节点的最终位置通常需要随工作流保存；“鼠标正在拖动”属于临时交互状态。不能简单按是否涉及视觉来判断数据归属。

### 2. 编辑器状态：现在怎样看和操作

例如当前选中的节点、画布缩放比例和打开的菜单。这些不应决定生成任务实际使用什么输入。

视口可以按体验需要保存为用户偏好；菜单、拖动等临时状态通常无需长期保存。

### 3. 运行状态：这次实际提交了什么

同一个节点可以有多次运行，每次运行有独立身份。运行输入在提交时固定，后续修改节点参数不得改变它。

前端只需维护当前相关任务，不必把所有历史加载进内存。如果后端已有生成记录能够提供这些信息，应复用或补充现有记录，而不是重复建设同义系统。

### 4. 界面仍然是一个节点

节点组件分别读取不同来源的数据：输入框读取工作流参数，选中边框读取编辑器状态，进度和结果读取相关运行状态与资产信息。

拆分仓库本身不保证性能。组件仍需只订阅自身需要的数据，避免选中或拖动一个节点导致所有媒体节点重新渲染。

## 五、建议的一次生成流程

以下为实现建议，尚不代表已完成的代码。

1. **读取当前输入**：读取本节点参数，以及上游当前成功输出的资产。
2. **校验输入**：检查必填参数、输入类型、素材可用性和模型限制。
3. **准备提交快照**：读取本次提示词、模型配置和素材引用；若有未保存编辑，先保存并取得修改版本，或使用双方明确约定的随请求提交快照协议，不能让后端默默执行旧文档。
4. **提交生成**：携带重复提交防护标识和版本信息；后端校验并固定权威输入快照，建立运行身份，关联任务编号，回传实际采用的输入。前端预览与后端实际输入不一致时不能静默替换。
5. **更新进度**：更新对应运行记录，建议保留旧结果并显示生成状态。
6. **保存新结果**：由后端持久化新资产及创作信息，使其可在资产库中查询。
7. **切换节点输出**：确认新结果后，将节点当前输出指向新资产，不删除旧资产。
8. **下游再次运行**：重新读取上游当前输出，因此默认使用新结果。

### 异常与一致性建议

- 新生成失败时，保留旧结果并展示失败状态，不先清空节点。
- 上游更新不自动触发下游重跑，与首期手动生成定位保持一致。
- 提交后用户修改参数，不影响正在运行任务的输入。
- 节点组件卸载或移出视口，不等于取消后端任务。
- 刷新后应通过持久化任务信息恢复查询，不重新提交同一个生成请求。
- 首期可限制同一节点同时提交多个任务，以降低结果乱序覆盖的复杂度；若允许并发，必须明确哪个运行可以更新节点当前输出。
- 上游正在重新生成但尚未成功时，建议仍以其现有成功结果作为可用输入，并明确显示生成状态。

## 六、前后端需要约定的最小信息

以下为概念字段，不是最终接口字段名。

| 对象 | 需要识别的信息 |
| --- | --- |
| 工作流 | 工作流编号、所属项目或用户、格式版本、修改版本、节点与连接 |
| 节点 | 节点编号、类型及定义版本、当前参数、位置、当前输出资产 |
| 连线 | 来源节点及输出口、目标节点及输入口 |
| 一次运行 | 运行编号、所属工作流和节点、文档版本、后端任务编号、实际输入及来源运行、状态与错误 |
| 生成资产 | 资产编号、关联生成记录、展示及模型输入所需的媒体信息 |

需要特别注意：

- 资产创作详情读取生成时的真实参数，不能直接读取节点当前参数。
- 保留资产的工作流或节点来源，避免旧结果进入资产库后无法查找归属。
- 素材身份优先通过资产编号表达，不仅依靠可能变化的地址。
- 区分原始素材、展示缩略图和下载地址，避免把展示地址错误提交给模型。
- 浏览器状态仓库不等于后端持久化；工作流保存与任务回读必须单独实现。

## 七、首期范围与后续演进

### 首期建议完成

- 节点与有明确输入输出含义的连接。
- 工作流保存和刷新恢复。
- 单节点手动生成、输入快照和任务状态恢复。
- 成功后切换当前结果，失败时保留旧结果。
- 旧结果进入资产库，并可查看真实创作信息。
- 下游下次生成使用上游当前成功输出。

### 可以暂缓

- 节点专属历史面板。
- 整张画布历史版本与回滚。
- 整条工作流自动调度。
- 条件分支、循环和复杂子工作流。
- 多人实时协作。

### 为未来全局智能体保留的基础

将创建节点、修改参数、连接节点组织为独立编辑操作。用户与未来智能体复用编辑操作及校验，不将业务逻辑全部写在按钮点击回调中。运行节点属于独立的执行能力，只向获得授权的用户执行入口开放；共用技术模块不意味着共用执行权限。

未来长任务的可靠执行应由服务端持久化状态并负责调度，不能依赖浏览器持续打开，也不能只依赖对话记录恢复执行。

## 八、建议的首个验证闭环

采用“文本输入 → 图片生成 → 视频生成”的小范围流程，先验证真实数据与任务关系，再扩展节点种类。

验收至少覆盖：

- 图片重新生成成功后，节点展示新图，旧图仍可在资产库查找。
- 旧资产详情显示旧提示词，不被节点当前参数污染。
- 视频任务提交后，上游变更不影响该次视频任务。
- 视频下一次生成默认使用上游新图。
- 生成失败时旧结果不丢失。
- 刷新后恢复任务，不重复提交。
- 旧任务结果不会错误覆盖较新的当前结果。

## 九、工程方向与设计取舍

真正要解决的问题是：首期实现可靠的手动节点创作台，同时允许将来扩展模板、全局执行和智能体辅助编辑，不因新增入口重写数据与任务逻辑。

- 支持提前设计：节点身份、端口、运行快照和资产来源一旦混在组件状态里，后续保存、恢复、模板和自动编排都容易返工。
- 反对过度设计：需求尚未明确时构建通用调度器、插件平台或多人协作框架，会增加首期成本，且未必符合实际需求。
- 当前取舍：先建立清晰模型、明确操作入口和可测试协议；只实现验证闭环需要的能力。不要为了“未来可能有”建立空目录、万能基类或庞大的命令框架。
- 可能改变方案的变量：目标节点与媒体规模、同节点并发策略、全局执行语义、多人编辑需求。这些可以后续确认，不妨碍先建立文档与运行分离的基础。

## 十、React Flow 的使用边界

### 1. 让库负责交互，不让库决定业务

React Flow 负责节点与连线展示、视口、选择、拖动和连接交互；业务侧负责端口类型、模型参数、资产引用、权限、运行和保存。自动布局、执行调度、业务撤销和服务端持久化不能被假定为引入画布库后自然具备。

已安装 `@xyflow/react@12.11.6`，依赖声明与 npm 锁文件已更新。依赖检查未报告 React 冲突，现有项目构建通过；尚未接入画布，因此不能视为已完成浏览器运行兼容性验证。实施时阅读该版本对应文档并验证实际节点。

### 2. 建立受控的数据映射

- 工作流文档作为业务事实来源，经显式映射得到 React Flow 的 `nodes`、`edges`；不要长期维护两份可以分别修改的业务节点数组。
- 通过 `onNodesChange`、`onEdgesChange`、`onConnect` 等交互入口分类处理变化；拖动中允许内存高频更新，拖动结束形成一次编辑提交与保存调度。
- `nodeTypes` 等注册映射保持稳定；节点组件按类型注册，不在页面渲染过程中反复创建组件类型。
- 端口使用稳定编号映射到 `Handle` 的 `id` 与连接的 `sourceHandle`、`targetHandle`，不能用数组下标或显示文案作为长期身份。
- 动态改变端口布局时，按所选版本要求更新节点测量信息；图片加载和节点尺寸变化后也要验证连接点位置。
- 后端保存白名单字段，不直接把 React Flow 的整个内部对象序列化；测量信息、临时选择状态和回调不得进入业务协议。

### 3. 坐标、输入与样式

- 明确屏幕坐标和画布坐标，素材拖入等场景使用库提供的坐标转换能力，不自行重复推算缩放与偏移。
- 对输入框、滚动区域等按库规范使用 `nodrag`、`nopan`、`nowheel` 等交互隔离机制，并实测，不能只全局阻止事件传播。
- 输入框、富文本、中文输入法组合输入期间，画布删除和快捷键不得误触发；浮层关闭与焦点恢复也要测试。
- 画布容器需要可测量的稳定宽高；侧栏展开、窗口变化、不同缩放比例下验证布局。页面弹层与画布内浮层分清坐标系和层级。
- React Flow 默认样式仅作底层基础，业务外观遵循项目深色主题、设计稿与 Token；禁止为接库顺带改版。

## 十一、项目目录与模块职责

以下是建议归属，不是要求一次性创建全部文件。文件命名、结构索引和依赖方向遵循项目规则。

| 位置 | 建议职责 | 禁止承担 |
| --- | --- | --- |
| `src/pages/WorkflowPage.jsx` | 页面上下文、加载与订阅生命周期、区块组合 | 节点表单全集、图遍历和请求协议细节 |
| `src/components/workflow/` | 画布适配、节点外观、工具栏、参数区、域内编辑操作与校验 | 反向读取页面闭包、复制其他页面整套状态 |
| `src/hooks/` 或工作流业务域内 Hook | 按职责组织保存、运行观察和恢复 | 把所有逻辑搬进一个巨型 Hook |
| `src/stores/` | 工作流文档、编辑器状态、运行状态及局部选择器 | 用状态仓库替代服务端持久化 |
| `src/api/` | 工作流接口、鉴权请求复用、响应适配 | 引用画布组件或页面 |
| `src/config/` | 稳定节点能力定义及现有模型配置的关联 | 与服务端各自维护冲突的权威规则 |
| `src/utils/` | 真正跨域或无业务边界的纯工具 | 收容所有工作流业务逻辑 |

编辑操作、图校验和快照组装尽量保持可脱离 React 测试。运行协调由页面或业务 Hook 接线，节点组件只触发明确动作，不自行拥有轮询循环。共享任务管理能力应通过下层模块注入，不让 API 反向引用组件域。

### 现有能力的复用审查

- React、Zustand 和现有设计 Token 可继续使用，不需要为画布另建一套基础组件体系。
- 现有 `src/stores/creationStore.js` 主要组织创作分类和结果列表，不直接充当工作流模型。
- 现有 `src/api/creation.js` 的提交、轮询和结果适配可逐项评估复用；不能未经审计就把不同媒体接口当成完全统一的任务协议。
- 提示词、模型参数和媒体预览组件需检查 props、副作用和领域依赖后复用，不把完整创作页面复制进每个节点。
- 新建组件前检索组件资产清单与设计系统。仓库当前缺少规则中引用的 `docs/architecture/feature-development.md`；本规划不补造该文件，实施前需确认入口，期间遵循现有组件架构与导入规则。

## 十二、节点定义、连线与编辑操作

### 1. 最小节点定义

每种节点描述类型标识、定义版本、参数默认值、参数校验、输入输出端口及能力限制。端口至少表达稳定编号、媒体或文本类型、是否必填、单值或多值、数量限制。实际参数名待协议对齐，不在此提前定死。

客户端可共享协议描述或使用运行时结构校验；仅有编辑器类型提示不能验证接口、导入文件或智能体提供的数据。现有工程以 JavaScript 为主，可先使用明确的注释契约与运行时校验，不为此改造全仓语言体系。

### 2. 连线校验分两层

- 编辑时校验端口存在、类型匹配、数量约束、重复连接及自连接等结构规则；执行时再次校验素材就绪、访问权限和模型限制。
- 首期建议拒绝循环；若以后需要循环，必须增加明确执行语义，不能只解除前端限制。
- 多结果节点必须约定输出选择与顺序。首期若只支持单一当前输出，应显式限制，不让下游偷偷取数组第一项。
- 单输入口是替换连接还是拒绝第二条、模型切换导致旧端口失效如何处理，列为实现前的局部待约定项；不能静默丢失数据。

### 3. 编辑操作的公共入口

将新增、删除、修改参数、连接、断开和模板应用组织成有明确输入输出的业务操作。用户与智能体的编辑请求都经校验后更新文档，而不是直接任意改写状态仓库。

批量操作先整体验证，再作为一个编辑事务应用，避免半个模板写入。复制或模板实例化时统一生成新节点和连接编号、重映射内部端口引用，不复制任务身份；是否携带已有素材按模板协议明确。

撤销记录只管理编辑：一次拖动或一次模板应用作为一条记录；连续输入可按编辑会话合并。撤销不能撤销扣费、服务端运行或资产创建，也不能以旧整仓快照覆盖最新任务状态。删除节点后的任务结果应保留来源记录，但不得因回调重新创建已删除节点。

## 十三、保存、执行与并发的一致性

### 1. 自动保存不仅是防抖

工作流协议区分 `schemaVersion`（格式版本）与 `revision`（修改版本）。保存带预期修改版本，服务端检查后返回新版本；发生冲突时保留本地编辑并提供恢复途径，不静默覆盖。

建议首期每份文档串行提交保存，合并等待中的修改，并跟踪已确认版本与本地编辑序号。旧保存响应不能把仍有新修改的文档标记成已保存。关闭页面前的网络提交不可靠，必须显示未保存状态；本地草稿恢复可另行建设，但不能当成云端保存成功。

**特别注意：用户保存参数与后端更新节点当前输出是两个写入来源。** 应约定字段所有权或带版本的局部更新，避免前端拿旧文档整包保存，把后端刚产生的新输出覆盖掉。参数编辑、输出更新与客户端合并规则必须在接口契约中说明。

### 2. “最新成果”的确定时刻

第三节的业务规则保持不变：下游每次提交默认取上游最新成功成果，提交后冻结。实现上建议以服务端受理时的原子解析结果为准，并记录资产及来源运行；若界面已展示用户确认的具体输入，则携带期望的输出版本，变化时返回冲突供确认，不静默改用另一张图。最终采用哪一种受理协议需前后端一致约定，不能各自解释“最新”。

全局执行若后续实现，需要独立约定“本轮上游结果”与“运行前已有结果”的选择，不能直接循环调用节点按钮或并行提交所有节点。执行计划、拓扑顺序、失败传播和恢复由服务端协调，前端发起请求和呈现状态。

### 3. 重复提交与运行状态

- 客户端为一次用户执行意图生成幂等标识；网络超时后的重试复用同一标识，用户明确再次生成才创建新标识。服务端保存去重结果并校验相同标识的请求内容，不能只靠按钮禁用。
- 约定等待、执行、成功、失败、取消等状态及合法转换；轮询断开或客户端超时是观察失败，不直接把服务端任务判为失败。
- 请求超时但可能已受理时，先按幂等标识或运行记录核查；不得自动换标识再次提交付费任务。
- 进度事件携带运行身份和版本或序号，忽略重复、过期消息；旧进度不能把终态改回执行中。
- 首期建议同节点只允许一个活跃生成，后端也应检查；若允许并发，当前输出的归属规则必须由后端与前端一致执行，不能按“谁最后返回”决定。

### 4. 恢复与观察

后端提供当前相关运行查询，刷新后先获取权威状态，再恢复观察。轮询、服务端事件流或双向连接是传输选项，不需要首期全部支持；无论选择哪种，都要考虑重连、漏消息后的全量校准、退避、鉴权失效和清理订阅。

任务观察由工作流级协调模块管理，而不是每个节点各启动定时器。切换项目或工作流时清理旧观察，响应按工作流和运行身份隔离，防止晚到响应写入另一张画布。组件卸载只停止本地观察，真正取消执行必须调用后端支持的取消能力并确认结果。

## 十四、性能、资源与安全

- 节点按编号订阅自身字段，避免每个节点读取完整节点数组；保持未变化对象引用稳定。组件缓存不是替代合理状态粒度的万能办法。
- 图片节点优先缩略图，原始媒体按需读取；视频默认展示封面，限制同时解码和播放。临时对象地址及时释放，不写入持久化文档。
- 重型富文本、编辑弹窗和媒体处理按需挂载；视口裁剪应实测收益与测量代价，不能因节点卸载丢失任务或编辑数据。
- 文档不内嵌大体积媒体编码，不保存访问令牌或请求控制器。素材引用经过权限校验，导入模板和智能体数据限制大小、节点数量与支持类型。
- 自动布局属于纯布局能力，可后续引入专门库；布局不改变连接语义，不能移动节点时顺带修改业务输入。
- 用接近实际的媒体尺寸与节点复杂度做分档压测，例如 20、100、300 个节点；这些是测试档位，不是承诺容量。记录设备、边数、同时播放数、拖动帧耗时、交互延迟和内存增长，再确定支持范围。

## 十五、从零搭建的实施阶段

以下是架构层面的阶段划分，具体小阶段及实际进度见[开发计划表](./superpowers/plans/2026-09-22-node-workflow.md)。只有交付物与验证同时完成才能标记通过。

| 阶段 | 交付物 | 通过条件 |
| --- | --- | --- |
| 0：协议与契约 | 最小文档、节点定义、运行与资产协议；保存冲突、幂等和权限约定 | 前后端用同一组样例解释完整生成链路及失败场景 |
| 1：编辑器骨架 | React Flow 接入、少量真实节点、文档映射、基础编辑与保存 | 刷新恢复正确；缩放、中文输入和坐标转换可用；旧格式有明确处理 |
| 2：单节点纵向链路 | 提交快照、任务观察、结果切换、资产详情关联 | 成功、失败、响应丢失和刷新恢复均不串结果、不重复提交 |
| 3：节点依赖闭环 | 文本到图片再到视频，类型校验和最新输出解析 | 上游更新不改变已提交下游输入，下次运行采用新成果 |
| 4：工程加固 | 撤销、复制、保存冲突、异常处理及真实性能记录 | 边界测试通过，残留问题和支持范围有记录 |
| 后续：扩展能力 | 按已确认需求增加模板、用户全局执行、智能体编辑 | 复用已有协议与操作入口；智能体无扣费执行权限 |

不要先铺满全部节点类型再接保存与任务，也不要用纯前端模拟成功作为后端链路完成的依据。首个闭环应尽早接入真实后端，并使用受控测试任务验证扣费边界。

## 十七、开发前的防偏航检查

- 不把 React Flow 内部状态直接当成后端业务协议。
- 不把节点、运行、后台任务与资产编号混为一体。
- 不把旧资产参数改成节点当前参数，不用预览地址冒充模型输入。
- 不在节点组件里独立管理可靠任务生命周期。
- 不让参数修改、模板应用或智能体编辑隐式触发扣费。
- 不用防抖替代保存版本控制，不用按钮禁用替代服务端幂等。
- 不用撤销整仓快照覆盖最新运行状态，不用旧文档覆盖后端当前输出。
- 不在产品规则未确定时静默选择上游重跑、循环或多输出语义。
- 不为控制文件行数制造巨型 Hook 或无意义抽象，遵循项目职责边界。
