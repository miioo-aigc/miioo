# 项目资产图片编辑去重记录

记录日期：2026-10-13。主体角色图片重复问题已由 Suzy 手动验收通过；本文记录前端修复，不代表已经部署线上，也不代表后端所有重复入库场景已排除。

## 现象与证据

资产库 → 项目资产 → 角色：编辑图片保存后，所属角色详情已有新图，外层角色列表却又出现一张无名称、无描述的独立图片卡。

本次提供的响应中，资产列表新图 `id` 与主体候选记录 `asset_id` 相同，均为 `d6d95f1d-7158-4673-866d-491e0911ae2c`；候选记录自身 `id` 为 `98e1f73c-3ebe-4837-9a42-ff2f0b82279b`。新图已带正确主体归属、名称和描述，候选列表仅返回一次该资产。因此本例是前端重复展示，不能据截图认定后端保存了两个文件。

## 根因

1. `ProjectAssetCard` 将后端 `asset.images` 与本地 `edits.images` 直接拼接，未按真实资产编号合并。
2. 同一批本地结果又由 `CreationImageResultCard` 在外层输出，造成主体图片与主体卡片并列，缺少角色信息。
3. 前一轮修复只排除了分镜。随后主体修复误用接口类别 `character / scene / prop` 判断页面类别；页面实际传入 `chars / scenes / props`，导致两个修复分支均未执行。
4. 原测试只检查写入代码的条件，未核对页面真实传参，未能发现类别不匹配。

## 已实现方案

- `AssetsCards.jsx` 通过既有 `getAssetSubjectType(category)` 判断主体，不自行复制接口类别判断。映射源为 `src/utils/assetsBatchAdapter.js`。
- 角色、场景、道具的本地编辑结果进入所属主体详情，不再作为外层独立编辑结果卡渲染。非主体、非分镜原有行为保持不变。
- `ProjectSubjectImages.js` 的 `mergeProjectSubjectImages` 先遍历后端记录，再遍历本地记录，返回新数组，不修改输入、不删除持久化记录。
- 同记录编号可合并；未完成任务不按资产或地址合并。完成记录优先使用 `asset_id / assetId / creationAssetId / backendId`；两侧均有真实资产编号时，仅编号相同才合并。
- 缺少真实资产编号时，才以完全一致的原图地址兜底；不使用缩略图、源资产编号或创建时间判断重复。不同真实资产即使地址相同也保留。
- 后端返回前，本地记录补位；后端返回后，保留后端对象的编号、定稿状态和下载字段，抑制本地重复展示。不是删除云端图片或清空本地缓存。

## 分镜相关规则

分镜外层同样不再单独输出本地编辑结果卡；详情通过 `StoryboardMediaItems.js` 的 `mergeStoryboardMediaItems` 合并后端候选和本地结果。图片与视频分开判重，保留后端候选对象。详情排序为定稿置前，其余按创建时间升序，最新产物在最后。

主体与分镜使用各自的合并函数，不能把主体图片排序、编号语义或分镜混合媒体规则直接互换。本次明确的用户验收覆盖主体角色重复问题，不扩展宣称其他入口的全量人工验收。

人工复验：编辑后外层只保留主体卡；详情只新增一张结果；刷新、重新进入详情后仍只出现一次。保留源图，不改变定稿。

若再次重复，依次核对：页面分类实际值 → 外层卡片来源 → 后端资产列表 → 主体候选列表 → 本地记录的真实资产编号。先区分资产编号、候选记录编号和本地记录编号；需要真实响应时向用户索取，不能仅靠时间或外观判断，更不能盲目删除资产。

本次未修改保存接口和后端存储。此前 `edit-result` 返回 `404 {"detail":"图片不存在"}` 的问题与展示去重分开处理，不以前端降级绕过。

## 关联验收：创建时间

主体图片详情的创建时间已通过用户验收：`formatEastEightDateTime` 将带时区时间转为东八区；无时区日期时间按东八区解析，显示 `YYYY-MM-DD HH:mm:ss`。例如 `2026-10-13T06:34:53.519Z` 显示为 `2026-10-13 14:34:53`。只改变展示，不修改原数据或排序。对应测试为 `scripts/east-eight-time.test.mjs`，5 项通过（包含非东八区进程环境）。
