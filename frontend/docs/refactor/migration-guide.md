# 页面迁移指南

> 文档类型：页面和业务区块重构流程
> 最后更新：2026-07-16

## 1. 迁移原则

- 结构变化、行为不变：不改变接口协议、业务规则、用户流程和既有视觉，除非另有变更说明。
- 小步迁移：每次只处理一个页面或一个明确区块，不一次性重写超长页面。
- 先边界、后代码：先盘点状态和依赖，再抽组件；不能先移动 JSX 再补依赖。
- 复用优先、不过度抽象：视觉与交互相同的基础能力统一复用；只出现一次且强依赖页面的区块可以暂留页面。

## 2. 单区块迁移步骤

### 迁移前

1. 读取根规则、页面规则、架构规则和设计系统规则。
2. 阅读目标文件顶部结构索引；没有索引时先建立状态、数据流、组件和副作用地图。
3. 记录区块的 props、状态、setter、API、Store、ref、定时器、事件监听、回调、闭包变量和清理逻辑。
4. 确认目标目录：`ui`、`feedback`、`overlay`、`actions` 或业务域。
5. 写出原实现到目标组件的映射，以及保持不变的交互和参数。

### 迁移中

1. 优先抽纯展示区块，再抽稳定交互区块，最后处理 Hook 和动作。
2. 所有外部依赖显式改为 props、Hook 参数、Store 选择器或纯函数参数。
3. 保持回调名称、参数结构、API 字段和视觉 Token 不变。
4. 新组件通过业务域或目录入口导出，避免页面绑定内部文件路径。
5. 不要在同一轮顺手修改无关接口、样式或业务规则。

### 迁移后

1. 全局搜索旧组件名、旧导入路径、移动前的局部函数名和回调名。
2. 检查 import/export、默认导出、目录入口、循环依赖和未使用导入。
3. 重点搜索并验证 `ReferenceError`、`xxx is not defined`、undefined props、回调参数缺失和 effect 闭包问题。
4. 更新所有受影响文件的结构索引、组件盘点和迁移记录。
5. 运行定向检查、构建、架构检查和关键页面回归。

## 3. 引用安全清单

迁移前后必须逐项确认：

- [ ] 每个移动代码读取的状态和 setter 都有明确来源；
- [ ] 每个回调都已通过 props 或 Hook 参数传入；
- [ ] 页面局部变量没有被新组件直接引用；
- [ ] API、Store、工具函数和常量的路径真实存在；
- [ ] 导出名称与调用方名称完全一致；
- [ ] 依赖数组、AbortController、定时器和事件监听的清理逻辑未丢失；
- [ ] 同步生成、异步轮询、刷新恢复、失败清理等分支均保留；
- [ ] 关键打开、关闭、保存、删除、生成和错误流程可运行。

## 4. 验收命令

```bash
npm run lint
npm run build
npm run check:architecture
git diff --check
```

完整仓库 `lint` 失败时必须保留失败状态并记录错误来源；可以使用目标文件定向 ESLint 作为局部诊断，但不能把定向通过描述成全量通过。构建或架构检查失败时，迁移不能标记完成。

## 5. 页面迁移顺序

```text
ProjectList / GlobalSettings（样板）
→ ScriptPage
→ SubjectPage
→ AssetsPage
→ CreationPage
→ StoryboardPage
```

复杂页面先拆稳定区块，再处理状态 Hook 和任务流程。每完成一个页面，都要更新 `docs/refactor/component-inventory.md` 与 `openspec/changes/reorganize-frontend-components/tasks.md`。
