# 问题清单

本报告为持续审查记录，未完成全范围逐组件审查。不修改业务代码，不打开浏览器。位置以当前工作区为准；所有端到端表现待 Suzy 手动验证。P1 优先修复重要一致性问题，P2 为可恢复交互或状态问题。

## FND-001：登出后在途请求可以重新写入旧会话缓存

- 优先级：P1。证据：本地受控测试已确认缓存层行为；尚未确认真实账号间数据展示。
- 位置：`src/utils/cache.js` 的 `clearAllCache`、`fetchAndStore`；调用方 `src/api/request.js` 的 `clearTokens`。
- 证据：清空函数只删除已有缓存，不递增 `epoch`，不清空 `inflight`；清空前发起的请求仍通过代际判断并写入缓存。Node 测试在清空后释放旧请求，`peekCache` 返回旧会话数据。
- 影响：同一文档内鉴权失效后重新登录，旧数据可能重新进入共享缓存；是否实际显示取决于缓存键、请求时序和页面重载。不能据此声称已发生线上数据泄露。
- 修复：清空时切断旧代际请求的缓存写回和通知，清理去重表；旧请求结束时只能移除它自身的登记，不能删除新请求。调用方还需校验会话身份后再写入页面状态。
- 验收：延迟账号甲的查询，退出或触发鉴权失效，登录账号乙，再释放甲响应；乙的缓存、页面、订阅回调均不得收到甲数据。另测旧请求结束不破坏乙的并发去重。

## FND-002：创作单项和批量删除静默失败却移除本地卡片

- 优先级：P2。源码确认，运行表现待验证。
- 位置：`src/pages/CreationPage.jsx:552` 的 `deleteSelected`、`:640` 的 `handleDeleteCard`。
- 证据：删除 API 使用空 `catch`，不等待完成即调用 `deleteSelectedCards` 或 `storeDeleteCard` 并失效历史缓存。
- 影响：断网、无权限或服务端失败时，界面表现像删除成功；重新加载后资产可能再次出现。批量部分成功无法告诉用户失败项。
- 修复：按资产 ID 记录结果，成功后移除对应卡片，失败保留并提示；提供提交中状态和重复提交保护。若保留乐观删除，必须有逐项回滚与错误反馈。
- 验收：单项返回 500、批量部分失败、断网、重复点击；失败卡片仍可见且可重试，成功项刷新后不恢复，选择状态与实际结果一致。

## FND-003：通知列表缺少请求身份校验，失败被显示为空列表

- 优先级：P2。源码确认缺少保护；请求乱序影响待手动验证。
- 位置：`src/components/NotificationCenterModal.jsx:197`，`loadNotifications` 和打开弹窗的副作用。
- 证据：每次分类请求都无条件写入同一个 `notifications` 和 `loading`；无请求序号或清理。失败分支清空列表，未设置错误状态。
- 影响：创作通知的慢响应可能覆盖系统通知；旧请求先结束可能提前关闭加载态；接口失败显示“暂无通知”，无法区分真正为空。
- 修复：分类与打开周期共同限定请求归属，仅当前请求更新状态；区分空态、错误及重试。
- 验收：创作通知延迟 3 秒，系统通知延迟 0.2 秒，立即切换到系统；最终仅显示系统通知。再测关闭重开、500 和空数组三种情况。

## FND-004：管理员卡片显示开关的失败回滚覆盖其他并发操作

- 优先级：P2。源码确认，实际请求顺序待验证。
- 位置：`src/components/admin/AdminDisplaySettingsPage.jsx` 的 `handleToggleCardVisibility`、`CardVisibilityItem`。
- 证据：回滚保存整个 `previousItems`，失败时整表替换；`savingKey` 只记录一个正在操作的卡片，其他卡片仍可提交。
- 影响：先操作甲、再成功操作乙，甲随后失败时，会把乙已成功保存的状态在界面中回滚；单一忙碌标识也可能提前解除其他请求的禁用态。
- 修复：按卡片键管理忙碌状态及请求版本，失败只回滚该项；或明确采用整组串行提交。
- 验收：甲延迟失败、乙先成功，乙最终状态及刷新后的状态一致；同项不能重复提交，失败项可重试。

## FND-005：模型开放筛选项由两个不同范围的响应互相覆盖

- 优先级：P2。源码确认，最终表现取决于响应顺序。
- 位置：`src/components/admin/AdminModelVisibilityPage.jsx:77` 和 `:89`。
- 证据：当前列表第一页从 `payload.list` 提取服务商选项；另一个请求从前 100 条模型提取选项，两者都直接覆盖同一状态。前者受搜索、服务商和类型筛选限制。
- 影响：列表响应后到时，下拉菜单可能只剩当前页或当前筛选中的服务商；100 条预热也不能保证覆盖全部服务商。
- 修复：筛选选项使用独立完整服务商来源，不由当前页列表回写；服务端无完整来源时明确分页收集策略。
- 验收：准备跨页、跨服务商数据，交换两次请求返回顺序，搜索和切换分类后，下拉选项仍完整且稳定。

## FND-006：手机号验证与换绑把 HTTP 失败当作成功

- 优先级：P1。源码确认，运行表现待验证；不等同于后端允许越权换绑。
- 位置：`src/api/user.js:178` 至 `:225`，调用方 `src/components/ProfileModal.jsx:397` 和 `:459`。
- 证据：`authFetch` 对普通 400/422/500 返回 Response，不自动抛错。`apiVerifyPhoneCode` 不检查 `res.ok` 就返回 `{ valid: true }`；`apiRebindPhone` 直接返回 Response，调用方只判断是否为 null。因此业务错误响应仍会进入下一步或调用 `onBind(newPhone)`。发送验证码、解绑接口也未检查状态码。
- 影响：错误验证码被前端当成通过，换绑失败仍可能显示新手机号；实际后端资料未更改。发送验证码失败也可能启动成功倒计时。
- 修复：接口适配层统一检查 HTTP 状态并解析业务结果；页面只在服务端确认后更新资料，并补发送中、验证中和失败重试状态。
- 验收：验证、换绑、解绑分别返回 400/422/500 时不得进入成功步骤或更新资料；成功后重新读取账号手机号一致。慢网重复点击不得重复发送。核对真实接口是否应使用专用验证端点，不代替后端权限审查。

## FND-007：项目资产响应没有项目身份隔离

- 优先级：P2。源码确认，需手动验证乱序表现。
- 位置：`src/components/assets/AssetsProjectPanel.jsx:282` 的 `loadFirstPage`、`:380` 的 `loadMorePage`、`:412` 的切换副作用。
- 证据：分页元数据按项目与分类区分，但展示数据只写入 `assetsMap[category]`；请求完成不检查当前项目。清理只取消尚未执行的动画帧，不能阻止已发出的请求写回。
- 影响：甲项目慢请求可能在切换乙后覆盖同分类列表，标题和卡片归属不一致。是否会进一步写错对象需要逐个操作回调补证，不作已确认数据损坏结论。
- 修复：展示数据按项目与分类共同存储，或者在首屏和加载更多的所有异步阶段结束后校验请求代际；切换时清理旧选择及详情。
- 验收：甲首屏慢、乙首屏快，以及甲加载更多时切乙两组场景，最终只显示乙数据，选择、详情和操作参数均属于乙。

## FND-008：分镜重排在状态更新函数中执行网络副作用

- 优先级：P2。源码确认。
- 位置：`src/pages/StoryboardPage.jsx:2316`、`:2344`、`:2361`、`:2398`；`src/main.jsx:7` 启用严格模式。
- 证据：新增、复制、删除和拖动的 `setShots(prev => ...)` 内调用重排 API；失败仅 `console.error`。React 状态更新函数应为纯计算，严格模式开发检查可能重复执行该函数。
- 影响：可能重复提交排序；接口失败时界面仍保留未持久化顺序，刷新后恢复旧顺序。不能据此声称生产环境每次一定发双请求。
- 修复：纯排序函数只返回数据；事件编排层或明确的串行保存队列负责重排请求、版本校验和失败反馈。保持当前页面集中编排的合理边界，不机械拆文件。
- 验收：严格模式下一次操作只有一次预期重排提交；连续拖动、重排失败、复制成功但重排失败均有确定反馈，重新进入顺序与服务端一致。

## FND-009：水印设置读取覆盖草稿，保存未校验接口失败

- 优先级：P2。源码确认。
- 位置：`src/components/WatermarkSettingsModal.jsx:34`、`:51`；`src/api/settings.js:8`、`:22`。
- 证据：初次 GET 未完成时开关和保存已可用，返回后直接覆盖草稿；GET/PATCH 都不检查 `res.ok`，PATCH 的普通 HTTP 错误仍使 `Promise.all` 成功结束，弹窗提示保存成功。
- 影响：慢网下用户设置被旧值覆盖；批量服务商部分失败仍假成功。首个服务商代表全局设置的产品语义尚待确认。
- 修复：区分读取、编辑、保存状态；校验每个响应并汇总部分成功项，失败保留草稿与重试入口。只在真实保存成功时提示已生效。
- 验收：延迟读取后先尝试编辑；单个服务商 PATCH 返回 500；GET 返回 500；必须不覆盖已编辑值、不提示假成功，重新打开与实际保存结果一致。

## FND-011：手机号登录失败没有面向用户的错误处理

- 优先级：P2。源码确认。
- 位置：`src/components/LoginModal.jsx:425` 的 `handleLogin`；`src/api/auth.js:4` 的 `readAuthResponse`。
- 证据：接口对错误验证码及服务异常抛错，点击处理函数直接 await，没有 catch、错误状态或提交锁；登录按钮也未传入提交中禁用状态。
- 影响：错误验证码或网络失败时用户没有明确失败反馈，等待中可重复提交。不能将“验证码发送按钮已有 catch”当作登录提交已处理。
- 修复：登录事件层捕获错误并展示可理解提示，增加请求中状态与重复提交保护，成功后才关闭弹窗。
- 验收：错误验证码、500、断网均有可见提示并可重试；慢请求连续点击只提交一次，成功后登录状态正常恢复。

## FND-012：剧本工作区加载失败被重新抛出，没有恢复入口

- 优先级：P2。源码确认错误处理缺口。
- 位置：`src/pages/ScriptPage.jsx:534` 工作区加载副作用、`:603` 错误分支。
- 证据：加载 catch 只打印错误后再次 throw，整条 Promise 没有下游 catch，也未设置工作区读取错误态。此问题与已有的编排任务轮询错误处理不同。
- 影响：无法恢复已有剧本时用户不能区分“项目没有剧本”和“读取失败”；重新操作可能基于不完整状态。实际覆盖数据风险尚未证实。
- 修复：读取状态单独建模，失败保留可重试入口；首次读取未确定前避免以空态开放有覆盖风险的动作。另行校验项目切换时旧响应身份。
- 验收：有剧本项目首次读取返回 500，必须明确显示读取失败且可重试；重试成功恢复原稿，不自动生成或清空原稿。
