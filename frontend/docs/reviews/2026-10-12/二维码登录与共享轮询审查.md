## WN-015-3A / P1：退出二维码登录流程后，旧结果仍可能提交认证状态

证据：serialPolling.js:30–37 在 await task 后不校验运行状态，stop 仅清定时器和可见性监听。WechatView 的轮询结果没有当前访问或二维码身份检查，旧回调操作共享 pollingRef，可能停止新的轮询；loadQrCode 也没有请求版本，旧二维码获取完成后仍可启动轮询，即使视图已经退出。关键写入位于 auth.js:144：轮询接口收到 access_token 立即 setTokens，先于页面处理结果；即使只在页面添加结果守卫，也不能阻止旧令牌写入。

前提：二维码获取/轮询请求未结束时关闭弹窗、切换手机登录、刷新二维码，或另一次登录改变身份，旧请求随后成功返回。可能后果：旧流程继续触发登录成功/绑定跳转，或覆盖新认证状态。源码与模拟确认缺少保护；没有执行真实账号切换，不声称已发生真实串号。

建议：对二维码获取和轮询建立访问代次及二维码身份；退出/切换/刷新立即失效，旧请求不启动后续动作；令牌提交前同时验证原认证代次和当前登录流程仍有效。只给组件加取消标记不足以覆盖 API 内令牌写入；所有调用 apiPollWechatQrCodeStatus 的路径（包括绑定手机号后补读）必须盘点。请求取消只是辅助，结果守卫必需。未发请求可停止，已发服务端动作不能承诺撤销。

## WN-015-3B / P2：共享串行轮询可因页面显隐产生重叠请求

证据：serialPolling.js:19–26 页面重新可见直接 schedulePoll；工具没有 inFlight 守卫。若上一请求尚未结束，新定时器到期会启动第二个请求。stop/start 也无代次隔离，旧完成可参与新循环调度。

影响：二维码登录和微信绑定两处真实调用均受影响。ProfileModal 已有业务 current 守卫，可保护失效访问，不代表同一有效访问中的请求已串行；重复 confirmed 仍可能重复读取资料或回调。

建议：共享工具统一运行代次、单飞锁、停止后的结果/错误抑制；隐藏时暂停，恢复后由当前请求结束再安排下一轮。保留原间隔和错误退避，不改业务二维码样式。避免为恢复主动并发补发。

## 双向论证与验收

目标：登录结果只属于用户仍在进行的那次登录；退出后旧请求不得接管当前身份。支持关闭即失效的最强理由是与明确退出动作一致，可避免旧流程覆盖新身份。反对的最强理由是手机已经扫码确认、电脑随后关窗时，本可完成的登录会被忽略，用户需要重新打开扫码。真正分歧是关闭表示取消，还是允许后台继续登录。

推荐关闭、切换登录方式或刷新二维码均使旧流程失效；重新打开按现有流程取新二维码。唯一待确认：是否按此规则修复。修复后验证：获取二维码/轮询慢响应时关闭及重开、切手机登录、另一账号登录、旧结果迟到；显隐切换及 stop/start 保持最多一条有效请求；旧结果/错误不影响新二维码；正常确认仅成功一次。真实服务端是否已建立会话须测试核验，不能承诺前端取消撤回服务器状态。
