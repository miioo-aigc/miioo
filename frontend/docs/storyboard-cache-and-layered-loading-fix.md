# 分镜缓存与分层加载修复记录

> 修复日期：2026-07-31；状态展示规则更新：2026-08-11
> 适用页面：分镜页面
> 关联入口：`PROJECT.md` 的 2026-07-31 记录

## 一、问题背景

分镜页面同时包含两类数据：

1. 文字和结构化数据：分镜描述、景别、运镜、拍摄角度、构图、时长、光影、环境音、旁白、主体引用和生成参数等。这些数据体积小，应该尽快展示。
2. 媒体数据：分镜图片、视频、视频封面、缩略图、候选媒体和定稿媒体。这些数据可能来自大体积文件或需要单独请求，加载时间明显更长。

页面原本存在几类容易误导用户的问题：

- 分镜列表接口返回的对象可能携带图片、视频和参考素材地址，直接把完整对象写入浏览器缓存，容易触发 `localStorage` 配额不足。
- `QuotaExceededError` 出现时，缓存层会降级到内存，但日志中的“持久化失败”容易让人误以为文字数据也获取失败。
- 缓存被清理、缓存为空或后端响应短暂为空时，页面可能把已有分镜误判断为未生成，显示“开始智能分镜”。
- 文字缓存可以秒开，但切换到其他页面再返回分镜页面时，媒体候选可能需要重新请求；首次尚未取得候选列表应有明确加载反馈，而已有候选媒体的后台刷新不能覆盖卡片并伪装成“正在生成”。
- 多个缓存恢复、分镜接口刷新和候选媒体请求可能并发，早结束的请求会提前关闭较晚请求的加载状态。

## 二、缓存分层规则

### 2.1 分镜列表缓存只缓存轻量数据

入口：`src/api/storyboard.js` 的 `compactStoryboardForCache`。

接口返回值不会被修改，只有写入缓存时进行压缩。当前分镜列表缓存保留文字和结构化字段，媒体候选继续通过单独的 `media-candidates` 接口读取。

写缓存前会处理以下内容：

- `image_url`、`video_url`、`imageUrl`、`videoUrl` 等大媒体字段。
- `thumbnail_url`、`poster_url` 和参考图地址字段中的超大值。
- `data:` 开头的内嵌图片数据。
- 长度超过 `200000` 字符的字符串值。
- `gen_params` 中的 `creation_form` 大对象。
- `gen_params` 内明显过大的供应商响应或媒体数据。

这里的目标不是删除所有媒体信息，而是保证文字缓存可持久化；较小、对详情恢复有用的字段仍可保留。

### 2.2 `cache.js` 支持写入时序列化

`cached()` 增加 `serialize` 选项：

```js
cached(key, fetcher, {
  medium: MEDIUM.CONTENT,
  ttl: TTL.CONTENT,
  serialize: (data) => data.map(compactStoryboardForCache),
});
```

数据流如下：

```text
后端完整响应
  -> 页面正常消费完整响应
  -> 写入缓存前 serialize
  -> localStorage 只保存轻量分镜文字/结构数据
  -> media-candidates 单独请求图片/视频候选
```

因此，缓存压缩不会导致当前页面丢失后端返回字段，也不会要求详情弹窗从压缩后的缓存中加载原始视频。

### 2.3 `QuotaExceededError` 的处理顺序

当 `localStorage.setItem()` 触发 `QuotaExceededError` 时，缓存层按以下顺序处理：

1. 仅针对 `storyboards:` 缓存键，清理其他旧的分镜缓存键，不主动清理无关业务缓存。
2. 使用已经压缩过的当前缓存再次写入。
3. 如果清理后仍然超出配额，写入 `memStore`，让当前页面继续使用这份数据。
4. 保留警告日志，便于发现浏览器空间问题，但不让缓存异常阻塞页面。

这意味着：

- `QuotaExceededError` 首先表示“本次持久化失败”，不等同于“接口请求失败”。
- 文字数据通常仍然在当前请求结果、React 状态或内存缓存中，页面可以继续显示。
- 如果用户刷新浏览器，内存降级数据会消失，页面会重新请求接口；因此不能把内存降级当成跨刷新缓存。
- 如果希望长期避免警告，应清理旧的分镜缓存或确认部署后的压缩逻辑已经生效，而不是把完整媒体对象重新写回缓存。

## 三、分镜页面加载顺序

### 3.1 首次刷新

无可用文字缓存时：

```text
进入分镜页
  -> 请求分镜列表接口
  -> 分镜文字/结构数据返回
  -> 渲染镜头行
  -> 每个真实分镜镜头请求 media-candidates
  -> 分镜列、时间轴显示局部 DotsLoading
  -> 候选媒体返回
  -> 移除对应镜头加载动画并显示图片/视频/定稿状态
```

整页加载只用于文字和结构数据尚未到达的阶段。文字数据到达后，媒体慢请求不会再阻塞整页文字展示。

### 3.2 切换页面后返回

有文字缓存时：

```text
返回分镜页
  -> 立即读取文字缓存
  -> 文字和结构字段秒开
  -> 按需重新请求 media-candidates
  -> 已有候选媒体保持原卡片可见，在后台更新候选和定稿状态
  -> 首次尚未取得候选列表的镜头显示局部加载动画
  -> 媒体候选请求完成后更新分镜列和时间轴
```

这里的“秒开”只针对文字和结构数据，不代表原始视频已经缓存在浏览器。媒体候选仍可能每次重新请求；只要本轮请求尚未完成，就必须保持动画。

## 四、空数组与失败态保护

### 4.1 缓存空数组不代表真实无数据

分镜页面订阅分集缓存和项目全量缓存时，收到空数组只保留当前状态，不直接执行 `setIsLoadingEpisode(false)`。需要等待分镜接口请求确认，避免以下情况误显示空态：

- 旧缓存被配额清理。
- 轻量缓存尚未写入。
- 分集对象和分集 ID 异步到达，首次读取使用了不完整信息。
- 项目全量缓存尚未完成更新。

### 4.2 分镜接口空数组的二次确认

当前分集接口返回空数组时，页面会再请求项目全量分镜并按当前 `episode_id` 过滤。只有二次确认后，才决定真实状态。

页面还会读取当前分集的 `status`、`storyboard_count` 等字段：

- 明确是 `pending`、`draft`、`initial` 等未生成状态：允许显示“开始智能分镜”。
- 有分镜数量或状态为 `storyboarded`、`generated`、`videos_ready`、`no_image`、`images_ready`、`edited`：空响应视为加载异常。
- 分集信息缺失或状态不明确：保守视为加载异常，避免已有数据被误判为未生成。

加载异常态文案为“抱歉，加载数据失败，请刷新重试”，其中“刷新”为蓝色可点击操作。

## 五、媒体加载状态实现

### 5.1 分镜列

`StoryboardShotMediaColumn` 的 `loading` 只表达候选媒体的首次加载，不表达已有媒体的后台刷新：

- 没有媒体时显示居中的 DotsLoading。
- 已有候选媒体或主记录兜底媒体时，刷新期间保持原卡片可见，不叠加 DotsLoading，避免被误认为当前镜头正在生成。
- 真正的生成中占位继续由当前镜头的待生成候选和任务状态控制，与媒体列表刷新状态分离。

### 5.2 时间轴列

`StoryboardFinalizedCard` 的 `loading` 同样只用于首次尚未取得候选媒体列表的镜头：

- 没有定稿媒体时显示加载动画。
- 已有定稿媒体时，后台刷新不覆盖显示加载动画；本轮结果返回后仅更新定稿状态和媒体数据。
- 媒体原图、视频地址和定稿编号在刷新期间保持稳定，避免加载动画与生成中状态混淆。

### 5.3 请求版本控制

`StoryboardPage` 使用 `mediaRequestVersionRef` 按镜头记录媒体请求版本：

1. 每次 `loadShotCandidates` 为镜头发起请求时递增版本并标记 loading。
2. 请求结束时，只有当该镜头的当前版本仍等于本次版本，才允许关闭 loading。
3. 如果期间又发起了新请求，旧请求只能更新它拿到的数据，不能关闭新请求的动画。

另外，渲染层会把“真实后端镜头且 `candidateMediaMap` 尚无该镜头结果”视为首次 loading，防止 React 状态更新顺序造成短暂无动画窗口；一旦已有该镜头的候选数组，即使后台刷新请求进行中，也不再覆盖卡片为加载动画。

## 六、数据边界与已知限制

- 浏览器不会因为缓存了文字 JSON 就自动缓存原始视频；视频是否命中 HTTP 缓存由浏览器、响应头和媒体 URL 决定，不能由当前前端 `localStorage` 缓存逻辑保证。
- 前端只在媒体候选首次读取期间显示局部加载反馈，不把完整视频写入 `localStorage`；已有媒体的后台刷新不改变卡片的生成状态表达。
- 如果后端 `media-candidates` 返回成功但数组为空，前端会结束该镜头的媒体请求状态；这表示候选接口已经给出结果，不代表一定有可播放媒体。后端应确保候选接口在媒体尚未准备好时返回明确状态或封面字段。
- 如果候选接口请求失败，页面会回退到分镜主记录中的 `storyboardImage`/`storyboardVideo`；此时加载动画会结束，并保留主记录媒体作为兼容展示。
- 这次记录的是前端缓存和加载反馈修复，不涉及后端视频转码、封面生成、HTTP 缓存头或 CDN 配置。
