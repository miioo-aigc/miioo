# 主体页面 Seedance 虚拟素材认证查询记录

> 记录日期：2026-08-24
> 目的：保留本次讨论和实现方案，后续重新开发时无需重复梳理需求。

## 一、要解决的问题

主体页面的角色 Tab 需要展示当前角色定稿图的 Seedance 素材认证状态。

认证状态不应区分素材最终属于真人素材还是虚拟素材，只要当前角色使用的定稿图已经通过 Seedance 素材认证，就应展示「已认证」。

项目名称是可修改的展示字段，项目改名后，已经认证的素材仍然应该能够被查询到，不能因为项目名称变化而丢失认证状态。

## 二、现有接口数据

### 1. 角色接口

角色数据包含：

```json
{
  "id": "角色 ID",
  "project_id": "项目 ID",
  "name": "沉香",
  "primary_asset_id": "项目资产 ID"
}
```

其中 `primary_asset_id` 表示角色当前使用的定稿图资产 ID。

### 2. Seedance 素材组接口

```text
GET /api/live-materials/groups
```

接口能够返回真人素材组和虚拟素材组。虚拟素材组通过以下字段识别：

```json
{
  "id": "素材组 ID",
  "group_type": "AIGC",
  "name": "虚拟素材组名称",
  "auth_status": "verified"
}
```

### 3. 素材列表接口

```text
GET /api/live-materials/groups/{group_id}/assets
```

虚拟素材记录目前可返回：

```json
{
  "id": "素材记录 ID",
  "group_id": "素材组 ID",
  "upstream_asset_id": "上游素材 ID",
  "name": "沉香.png",
  "status": "Active"
}
```

`status = Active` 表示该虚拟素材已经通过认证。

### 4. 真人认证查询接口

```text
GET /api/live-materials/projects/{project_id}/subject-bindings
```

真人认证结果中可以通过 `subject_id` 和 `primary_asset_id` 精确对应角色当前定稿图，并依据 `status` 判断认证状态。

## 三、本次验证结论

已经验证：

- 虚拟素材存在素材级状态字段，`status = Active` 可以表示认证通过；
- 虚拟素材组和角色素材之间目前没有通过前端响应明确返回稳定关联；
- 虚拟素材的 `upstream_asset_id` 与角色接口的 `primary_asset_id` 不是同一格式，不能直接比较；
- 素材名称和角色名称相同，只能作为临时推断，不能作为长期可靠的资产关联；
- 如果项目名称和虚拟素材组名称相等或存在前缀关系，前端可以通过名称找到素材组；
- 项目名称修改后，名称关系断开，前端无法继续找到原虚拟素材组，因此认证状态会显示为「去认证」。

## 四、最终需求口径

项目名称不应参与认证关系判断。

项目改名后，已认证素材必须继续可查。前端需要基于稳定 ID 完成以下关系：

```text
当前项目 ID
  -> 对应的 AIGC 虚拟素材组
  -> 对应的虚拟素材
  -> 当前角色的 primary_asset_id
  -> 素材 status
```

认证状态判断应统一为：

```text
当前角色 primary_asset_id
  与认证记录中的原始项目资产 ID匹配
  且 status 为通过态
  => 已认证
```

## 五、后端最小字段需求

为避免项目名称、素材组名称和角色名称带来的误判，后端应补充稳定关联字段。

### 推荐字段

虚拟素材组返回：

```json
{
  "id": "素材组 ID",
  "project_id": "项目 ID",
  "group_type": "AIGC"
}
```

虚拟素材返回：

```json
{
  "id": "素材记录 ID",
  "group_id": "素材组 ID",
  "source_asset_id": "角色定稿图对应的项目资产 ID",
  "status": "Active"
}
```

`source_asset_id` 也可以命名为 `primary_asset_id`，但必须明确表示提交认证时对应的项目原始资产 ID。

### 可接受的替代方式

如果后端不希望在素材组和素材接口中分别补字段，也可以让项目级认证查询接口直接返回统一结果：

```json
{
  "subject_id": "角色 ID",
  "primary_asset_id": "角色定稿图资产 ID",
  "status": "active",
  "source": "AIGC"
}
```

只要前端能够通过角色当前 `primary_asset_id` 精确匹配认证记录即可。

## 六、前端正式实现方向

后端补充稳定关联后，前端不再使用以下字段推断认证关系：

- 项目名称；
- 素材组名称；
- 角色名称；
- 文件名；
- 图片 URL；
- `upstream_asset_id` 与 `primary_asset_id` 的猜测比较。

前端应改为：

1. 通过项目 ID 查询对应的 AIGC 素材组；
2. 查询素材组下的素材；
3. 用素材的 `source_asset_id` 或 `primary_asset_id` 匹配角色当前 `primary_asset_id`；
4. 将 `Active`、`approved` 等通过态转换为「已认证」；
5. 将 `pending` 转换为「审核中」并继续轮询；
6. 将 `failed`、`rejected` 等转换为「认证失败」。

真人认证和虚拟素材认证最终使用同一套角色卡片状态判断，不再按认证来源分支展示。

## 七、本次已撤销的临时方案

本次曾实现过以下临时兜底方案，但已撤销，不作为正式业务逻辑：

- 按项目名称匹配 AIGC 虚拟素材组；
- 项目名称无法匹配时无法查询虚拟素材认证；
- 按角色名匹配素材文件名；
- 以虚拟素材 `status = Active` 作为认证通过；
- `subject-bindings` 失败时继续查询虚拟素材；
- 角色列表异步加载完成后重新查询认证状态。

这些方案只能在数据没有稳定关联字段时临时验证，存在跨项目同名角色误匹配风险，因此不应重新直接用于正式逻辑。
