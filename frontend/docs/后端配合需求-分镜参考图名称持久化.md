# 需求：分镜「主体参考」参考图的名称持久化与展示

## 一句话背景

分镜页面「主体参考」列可以从资产库选入图片，或本地上传图片作为「参考图」。
在「创作分镜图」/「创作视频」两个弹窗的提示词输入框里输入 `@` 会弹出下拉菜单，
列出这些参考图供快捷引用。当前存在两个问题：

1. 同一张参考图在「创作视频」弹窗里的标签颜色和名称，与「创作分镜图」弹窗不一致；
2. 用户上传/选入多张不同的图，`@` 下拉里全部显示成「参考图」，无法区分谁是谁。

问题 1、以及问题 2 在「未刷新的当前会话内」，已由前端修复。
问题 2 在「刷新页面后」名称丢失，属于数据没有持久化，**必须后端配合**才能根治。

本文档给前端同学和后端同学同时看，分别列出各自要做/已做的事。

---

## 一、问题 1：标签颜色/名称在两个弹窗不一致（前端已修复，后端无需改）

### 现象
从资产库上传一张创作资产图后：
- 打开「创作分镜图」弹窗，`@` 下拉里该图显示为「【参考图】（紫色标签）」；
- 打开「创作视频」弹窗，`@` 下拉里同一张图显示为「【其他】（灰色标签）」。

### 原因
两个弹窗构造 `@` 下拉数据的逻辑不同：
- 「创作分镜图」弹窗（`imageReferenceItems`）：参考图统一标为 `_type: 'image'` → 紫色「参考图」；
- 「创作视频」弹窗（`videoReferenceItems`）：非「角色/场景/道具」的项被强制标为 `_type: 'other'` → 灰色「其他」。

同一张本地上传/选库的参考图，本质就是「参考图」，不该被归成「其他」。

### 前端处理（已完成）
`videoReferenceItems` 中，非真实主体（char/scene/prop）的项改为 `_type: 'image'`，
与「创作分镜图」弹窗保持一致（紫色标签、名称「参考图」）。

### 后端
无需改动。

## 二、问题 2：多张参考图名称无法区分（前端已做兜底，根治需后端配合）

### 现象
用户在「主体参考」列先后上传/选入两张内容不同的图，
在 `@` 下拉里它们都叫「参考图」，仅凭名称完全无法分辨。

### 原因（关键，请后端同学重点看）

分镜保存时，参考图只存了 URL，**名称没有被持久化**。

前端保存分镜（`toBackendStoryboard`）时，参考图字段是这样发出去的：

```js
reference_image_urls: (shot.mainRefs || [])
  .filter(...)
  .map(ref => ref.url)   // ← 只取 url，name 被丢弃
```

对应后端接口：
- `POST /api/projects/{projectId}/storyboards`
- `PATCH /api/projects/{projectId}/storyboards/{storyboardId}`

请求体里 `reference_image_urls` 是一个**纯 URL 字符串数组**，没有名称信息。

刷新页面时，前端从 `GET /api/projects/{projectId}/storyboards` 拿到的也只是这个纯 URL 数组，
于是每个 URL 只能兜底成同一个名字「参考图」，多张图就全都一样了。

一句话：**因为后端存的是 `["url1", "url2"]` 而不是 `[{url, name}]`，名称在保存那一刻就丢了，刷新后前端无从恢复。**

### 前端现状（临时兜底，已完成）

1. **当前会话内（选入后未刷新）**：名称是对的。
   从资产库选图时会带上资产的 `name`（创作资产没有 name 时用 `prompt` 前若干字符），
   `@` 下拉直接显示这个真实名称，能区分不同图。
2. **刷新后**：真实名称已丢，前端退而用 URL 文件名兜底。
   但创作资产的文件名是一串 UUID，展示出来像个 id，可读性差。
   （这一步只是「至少各不相同」，并非理想效果。）

### 需要后端配合（根治方案）

把参考图从「纯 URL 数组」升级为「带名称的对象数组」，让名称跟着数据一起持久化。

建议新增字段 `reference_images`（保留旧的 `reference_image_urls` 以兼容）：

```jsonc
{
  // 旧字段，建议保留以向后兼容
  "reference_image_urls": ["https://.../a.jpg", "https://.../b.jpg"],

  // 新字段：每张参考图带上名称
  "reference_images": [
    { "url": "https://.../a.jpg", "name": "赛博朋克街道" },
    { "url": "https://.../b.jpg", "name": "女主特写" }
  ]
}
```

要求：
1. `POST` / `PATCH` 分镜接口能**接收并存储** `reference_images`（含 `url` + `name`）；
2. `GET` 分镜接口能**原样返回** `reference_images`；
3. `name` 的取值由前端在保存时提供（来自资产名称或 prompt 摘要），后端只需透传存取，无需自行生成。

后端支持后，前端会：
- 保存时发送 `reference_images: [{url, name}]`；
- 加载时优先读 `reference_images` 取 name，回退到旧的 `reference_image_urls`。

这样刷新后名称依然正确，问题 2 彻底解决。

## 三、涉及接口清单

| 用途 | 方法 | 路径 | 是否需后端改 |
|---|---|---|---|
| 分镜列表 | GET | `/api/projects/{projectId}/storyboards` | 是：返回体新增 `reference_images` |
| 新建分镜 | POST | `/api/projects/{projectId}/storyboards` | 是：接收并存储 `reference_images` |
| 更新分镜 | PATCH | `/api/projects/{projectId}/storyboards/{storyboardId}` | 是：接收并存储 `reference_images` |

## 四、分工小结

前端（本次已完成）：
- 问题 1：统一「创作视频」弹窗 `@` 下拉里参考图的标签为紫色「参考图」，与「创作分镜图」弹窗一致；
- 问题 2：当前会话内用真实资产名称；刷新后暂用 URL 文件名兜底（待后端支持后改为读 `reference_images.name`）。

前端（待后端支持 `reference_images` 后再做）：
- 保存分镜时发送 `reference_images: [{url, name}]`；
- 加载分镜时优先读 `reference_images` 的 name。

后端（本需求）：
- 分镜 POST/PATCH 接收并存储 `reference_images`（`url` + `name`）；
- 分镜 GET 原样返回 `reference_images`；
- `name` 只透传存取，不需自行生成。

---

## 五、验收标准

1. 上传/选入两张不同内容的参考图，`@` 下拉里显示两个不同的、可读的名称；
2. 刷新页面后，上述名称依然正确显示（不再退化成 UUID 或统一的「参考图」）；
3. 同一张参考图在「创作分镜图」和「创作视频」两个弹窗里，标签颜色和名称完全一致。

## 六、优先级

- 问题 1：已解决（前端）。
- 问题 2 会话内：已解决（前端）。
- 问题 2 刷新后：中高（需后端加 `reference_images` 字段，否则刷新后名称仍不可读）。
