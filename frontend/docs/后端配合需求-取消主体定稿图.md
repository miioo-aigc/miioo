# 后端配合需求：取消主体定稿图（清空 primary_image_url）

## 背景

主体页面（SubjectPage）的卡片封面由主体的定稿图（primary image）驱动，产品要求的完整逻辑是：

1. 初始封面为空，只显示占位图标；
2. 用户上传或生成一张图后，该图自动被设为定稿并渲染为封面；
3. 用户改设其他图为定稿，封面更新；
4. **用户取消定稿，封面回到空状态（仅占位图标）。**

第 1~3 条都正常。第 4 条**取消定稿**存在后端 bug，导致取消不生效。

## 问题（核心，必须后端修复）

复现：
1. 主体已有一张定稿图（封面正常显示）；
2. 在编辑面板取消该图的定稿；
3. 封面短暂变空；
4. **刷新浏览器后：定稿勾选状态没有回来（正确），但卡片封面又回来了（错误）**。

这一"半对半错"的现象是定位的关键，说明后端**只清空了一半状态**：

- 候选图（图片级）的 `is_primary` 被清掉了 → 刷新后右侧定稿勾选不复现 ✅
- 但主体（记录级）的 `primary_image_url` / `image_url` 没被清掉 → 主体列表接口仍返回旧图 → 封面复现 ❌

也就是说：**取消定稿时，图片级 `is_primary` 与主体级 `primary_image_url` 没有联动清空。**

### 前端两处数据源（帮助理解为什么会出现分叉）

- 卡片封面读的是**主体列表**接口的 `primary_image_url ?? image_url`
  （`GET /api/projects/{project_id}/subjects?type=...`）。
- 右侧定稿勾选读的是**主体详情**接口的 `candidate_images[].is_primary`。

后端只清了后者、没清前者，所以刷新后勾选没了、封面还在。

### 前端发出的请求

前端取消定稿时发起
`PATCH /api/projects/{project_id}/subjects/{subject_id}`，请求体为：

```json
{ "image_url": null }
```

意图是把该主体记录级的主图清空。但后端响应里，`image_url` 和 `primary_image_url`
**仍然是原来那张旧图**，`null` 没有写入：

```json
{
  "id": "3cb57207-...",
  "image_url": "/uploads/subjects/.../fc32e9ea....png",        // 期望被清空，实际未变
  "primary_image_url": "/uploads/subjects/.../fc32e9ea....png", // 期望被清空，实际未变
  ...
}
```

推断：后端在处理这个 PATCH 时，对请求体做了 `exclude_none`（或等价的"忽略 null 字段"逻辑），
把 `image_url: null` 当作"未传该字段"直接丢弃，因此**主体记录级的主图从未被清除**。
（图片级 `is_primary` 的清空走的是另一条路径，所以它清掉了，造成上面"半对半错"的分叉。）

此外，当前 API 里**没有任何清除主图 / 取消定稿的接口**，只有设置定稿的
`PATCH /api/projects/{project_id}/subjects/{subject_id}/images/{image_id}/set-primary`。

## 期望行为

取消定稿后，该主体应处于"无定稿图"状态，**记录级和图片级两处状态必须同时清空、保持一致**：

- 主体记录级：`primary_image_url` 变为 `null`，`image_url` 变为 `null`（若后端用它承载主图展示）；
- 图片级：该主体的所有候选图 `is_primary` 均为 `false`（这条目前已经做到了）；
- 主体列表接口 `GET /api/projects/{project_id}/subjects?type=...` 后续返回的 `primary_image_url` / `image_url` 均为 `null`；
- 候选图本身不被删除，仅解除定稿关系（用户之后可以重新选一张设为定稿）。

核心：把"清空图片 `is_primary`"和"清空主体 `primary_image_url` / `image_url`"做成联动，
不要只清其中一处。

## 需要后端修改（二选一，推荐方案 A）

### 方案 A（推荐）：让主体 PATCH 支持显式清空 image_url

- 让 `PATCH .../subjects/{subject_id}` 能区分"字段未传"和"字段显式传 null"。
- 当请求体显式包含 `"image_url": null` 时，真正把 `image_url` 与 `primary_image_url`
  置空，并把关联候选图的 `is_primary` 全部置为 `false`。
- 注意不要对整个请求体统一 `exclude_none`；至少对 `image_url` 要允许显式 null 生效。

### 方案 B：新增"取消定稿 / 清除主图"接口

- 例如 `DELETE .../subjects/{subject_id}/primary-image`
  或 `PATCH .../subjects/{subject_id}/images/{image_id}/unset-primary`。
- 效果同上：清空 `primary_image_url` / `image_url`，候选图 `is_primary` 全置 `false`。
- 若采用此方案，请提供接口路径、方法、请求/响应结构，前端会切换调用。

## 前端当前的临时兜底（后端修好后可移除）

后端未修复前，前端把"已取消定稿"的主体 id 存到 `localStorage`（按 projectId 分开），
在渲染时强制把这些主体的封面覆盖为空，使刷新后仍显示为空占位。

局限：这只是本机本浏览器的遮罩。换设备、清缓存、或其他客户端访问时，
服务端仍返回旧的 `primary_image_url`，残留封面会再次出现。
因此**必须由后端真正清空该字段**才能彻底解决。
