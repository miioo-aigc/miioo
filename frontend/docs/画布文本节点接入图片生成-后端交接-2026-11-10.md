# 画布文本节点接入图片生成 `reference_materials` 后端交接

日期：2026-11-10

状态：待后端自查/确认。前端已核实“文本内容确实发出”，未改代码、未联调，不是已修复待验。

涉及接口：

- `POST /api/creation/images/generate`
- `POST /api/creation/videos/generate`

## 一、问题现象

画布中把「文本节点」连到「图片节点」，文本节点的内容不会生效：

1. 文本节点写内容，例如「一只橘猫在窗边打哈欠」；
2. 从文本节点连一条线到图片节点（连线进入图片节点的参考输入）；
3. 在图片节点的输入框里另写提示词，例如「赛博朋克风格」，点生成；
4. 生成结果只体现输入框里的提示词，和文本节点的内容毫无关系。

用户侧的第一反应是“前端没把文本节点的内容发出去”。本次排查的结论是：**前端发了，但走的是独立字段 `reference_materials`，从不拼进 `prompt`。** 如果后端没有读取并消费 `reference_materials`，现象就完全吻合。

本次现场是图片节点；视频节点共用同一套 `reference_materials` 传递方式，一并列出供后端对照，但视频侧现象尚未单独复现确认。

## 二、前端完整链路（已核实）

| 环节 | 代码位置 | 行为 |
| --- | --- | --- |
| 连线落地 | `frontend/src/components/canvas/CanvasImageGeneration.js:80` | 文本→图片连线把文本节点 id 写进图片节点的 `data.imageSourceIds`，文本在这里被当作“参考素材源”，不是提示词 |
| 生成前收集上游 | `frontend/src/components/canvas/CanvasImageGeneration.js:122` | 按直连顺序把上游节点转成 `sources`：文本源带 `content`，图片源带 `asset` |
| 计算最终提示词 | `frontend/src/components/canvas/CanvasImageGeneration.js:132` | 输入框有内容时 `prompt` 只用输入框内容；只有输入框为空时，才把上游文本用 `\n\n` 拼成 `prompt`，并置 `usesTextAsPrompt=true` |
| 组装请求参数 | `frontend/src/components/canvas/UseCanvasImageGeneration.js:52` | 有输入框提示词时，上游文本放进 `referenceMaterials`；输入框为空时文本已并入 `prompt`，不再重复收集 |
| 图片请求体 | `frontend/src/api/creation.js:1438` | 发出 `prompt` 与 `reference_materials` 两个并列字段 |
| 视频请求体 | `frontend/src/api/creation.js:1553` | 同样发出 `reference_materials` |
| 编辑器里的 `@` 引用 | `frontend/src/components/canvas/CanvasPromptReferences.js:29` | 上游文本**不会**变成可 `@` 插入的引用项：`getCanvasPromptFiles` 要求 `asset.url`，纯文本节点没有 `asset` |

结论：上游文本只在两个位置之一出现，且互斥：

- 输入框**有**内容 → 文本在 `reference_materials` 里；
- 输入框**为空** → 文本被拼进 `prompt` 里。

也就是说，用户“既连了文本节点、又在输入框写了提示词”时，文本内容**只**在 `reference_materials` 里，`prompt` 里没有任何上游文本。

## 三、两种场景对比

| 场景 | `prompt` 字段 | `reference_materials` 字段 | 现象 |
| --- | --- | --- | --- |
| 输入框有提示词（用户反馈的场景） | 只有输入框内容 | 上游文本内容 | 后端不消费该字段时，文本完全丢失 |
| 输入框为空 | 上游文本拼接结果（`\n\n` 分隔） | 不发送（`undefined`） | 文本生效，因为已经进了 `prompt` |

这条对比也解释了为什么“输入框为空时文本能用、写了提示词后文本就失效”。

## 四、接口请求体示意

图片接口 `POST /api/creation/images/generate`，对应前端函数 `apiGenerateCreationImages`（`frontend/src/api/creation.js:514`）。只连文本节点的请求体近似：

```json
{
  "prompt": "赛博朋克风格",
  "model": "<model-id>",
  "resolution": "2K",
  "aspect_ratio": "1:1",
  "image_count": 1,
  "count": 1,
  "imageCount": 1,
  "reference_materials": [
    {
      "id": "<text-node-id>",
      "type": "text",
      "label": "文本",
      "content": "一只橘猫在窗边打哈欠",
      "resultId": null
    }
  ],
  "save_to_assets": true,
  "inherit_project_style": false,
  "session_id": "<session-id>",
  "shot_id": null,
  "project_id": "<project-id>"
}
```

要点：

1. 图片分支的 `reference_materials` 是**混合数组**：文本源是 `{ id, type:'text', label, content, resultId }`，图片源直接是 asset 对象。字段形状不统一，可能让后端误判或跳过。
2. 数组为空时前端**不发送**该字段（`undefined`），不是发空数组。
3. 视频分支 `reference_materials` 只含文本源（`frontend/src/components/canvas/CanvasVideoGeneration.js:231`），形状 `{ id, type:'text', label, content }`。
4. 视频请求里另有一份 `inputs` 快照（`CanvasVideoGeneration.js:228`），形状 `{ nodeId, content }`，但那是画布侧快照，不是发给后端的生成请求体。

## 五、关键证据：该字段不在 OpenAPI 契约里

当前仓库的接口契约副本 `frontend/src/api/openapi.json` 中：

- 全文不含 `reference_materials`、也不含 `referenceMaterials`；
- `CreationImageGenerateRequest` 的属性表里没有该字段；
- `CreationVideoGenerateRequest` 的属性表里也没有该字段；
- 两个 schema 的 `additionalProperties` 均为空（未声明 `extra = "allow"`）。

因此有两种可能，需要后端确认是哪一种：

1. 后端请求模型没声明该字段，FastAPI/Pydantic 默认忽略未知字段，`reference_materials` 被静默丢弃；
2. 模型声明了但下游组装 prompt / provider 请求时没有使用它。

无论哪种，**问题都不在前端是否发出**：前端确认 `fetch` 的 JSON body 里带了这个字段；最终文本语义有没有进模型，取决于后端是否读取。

## 六、需要后端自查/确认的点

1. `POST /api/creation/images/generate` 的请求模型是否声明并读取 `reference_materials`；若声明了，最终传给模型的 prompt 里是否真的合并了这些文本。
2. `POST /api/creation/videos/generate` 同样检查。
3. 若计划合并，请给出规则：拼接顺序（是否按数组顺序）、分隔符、是否加“参考文本 / 素材文本”包裹文案、与 `prompt` 的前后关系。
4. 若后端决定不消费该字段，请明确回复，前端再调整为把上游文本直接拼进 `prompt`（或使用后端指定的新字段），并同步修改本文档第二、三节的逻辑。
5. 生成任务落库时是否保存 `reference_materials`：任务重试、历史回看、刷新页面后能否复现同样的文本语义。
6. 任务详情接口能否回传“本次实际生效的 prompt”，便于前端与用户排查文本是否被合并。

推荐的快速验证方式（任选其一）：

- 在图片/视频 generate 的 handler 里打印收到的 body key，确认 `reference_materials` 是否到达；
- 用 Swagger 或 curl 直接发一个带 `reference_materials` 的请求，观察生成结果与日志；
- 检查请求模型是否声明该字段，以及 `extra` 策略是忽略还是报错。

## 七、结论

- 前端**没有漏发**文本内容：文本节点内容确实进入了发往后端的 `reference_materials` 字段。
- 前端**不会**把上游文本拼进 `prompt`（这是当前设计），因此后端不消费 `reference_materials` 时，生成结果与文本内容无关是必然结果。
- 最终是否生效，取决于后端是否读取 `reference_materials`。请后端按第五节、第六节自查后回复结论与处理方案。
