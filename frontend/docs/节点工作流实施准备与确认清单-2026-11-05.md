# 节点工作流实施准备与确认清单

日期：2026-11-05。阶段：方案 A，技术核查与测试准备；尚未修改业务逻辑。

## 1. 核查结论

可以先进行协议设计、测试用例准备和接口核实，不能直接宣布整套需求只改前端即可完成。以下是静态代码证据，不代表真实后端联调通过。本轮未请求真实生成、未写入远端画布，也未打开浏览器。

| 核查项 | 当前证据 | 实施要求 |
|---|---|---|
| 文档保存 | CanvasDocument.js 使用 schemaVersion=1，节点数据写入 records.props；递归移除媒体地址和临时值 | 候选可在前端形成结构化数据，但必须验证后端是否接受并完整返回新增嵌套字段 |
| 素材校验 | serializeCanvasNode 只对当前 data.asset 校验永久 UUID 和上传状态 | 需要逐项校验候选及历史引用，不能只校验定稿 |
| 恢复资产 | CanvasAssetResolver.js 主要收集当前 data.asset.asset_id | 扩展为所有保留结果的资产集合，按编号去重并保留结果身份 |
| 解析上限 | canvas.js 的 resolve-assets 每次最多 200 个资产；现有恢复测试覆盖 201 个分批 | 候选增多后必须继续分批；容量与分页不能靠静默截断解决 |
| 图片结果身份 | creation.js 按索引返回 imageAssetIds，图片回填按索引取编号 | 复用真实资产编号链路，覆盖缺项、部分成功和结果索引测试 |
| 视频结果身份 | UseCanvasVideoGeneration.js 构造的 asset 只有 URL、类型、来源和封面，没有 asset_id | 必须补齐真实编号链路；不能拿任务 ID、创作记录 ID 或 URL 冒充资产编号 |
| 保存并发 | apiUpdateCanvasDocument 发送 base_revision、client_save_id 等；已有保存会话测试覆盖丢响应重放、版本冲突 | 新历史必须加入同一受控保存流程，不另起无版本保护的覆盖请求 |
| 分享 | 公开画布接口不带登录凭证，节点按公开资产响应恢复 | 仅在前端隐藏历史不能保证隐私；服务端响应和资产授权须与公开范围一致 |
| 运行查询 | canvas.js 已有运行查询、取消和对账接口包装 | 包装函数存在不等于现有生成链路已支持持久化恢复；不承诺刷新续跑 |

历史交接文档曾提及 props 白名单。故“前端能序列化任意嵌套字段”不能推导为“后端会原样保存”。本轮没有服务端实现或正式接口往返响应证明新增字段受支持。

## 2. 后端核实清单

这些是技术协作事项，不要求产品代替开发判断。

1. 新增结果集合、候选批次、当前定稿引用、历史记录及执行快照，能否通过现有 PATCH 保存，并由 GET 原样返回？提供脱敏请求与响应样例。
2. 文档字段白名单、大小限制、结果数量限制与版本迁移策略是什么？超限必须明确失败，不能裁掉历史后返回成功。
3. 非定稿资产被历史引用后，是否仍能被 resolve-assets 授权解析？资产回收是否识别这些引用？
4. 视频结果响应哪个字段是永久资产 UUID？是否需要前端适配，或后端补字段？
5. 分享、复制画布、分享导入如何处理候选和历史资产权限？新增嵌套字段是否会意外出现在公开响应？

建议联调样例：一个任务节点含两个批次、三个不同资产编号，定稿来自旧批次，历史包含曾用定稿。执行保存、读取、解析，比较结果身份、批次关系和定稿引用完全一致。再验证无权限资产、缺失编号、版本冲突和超限响应。未取得样例前，状态为“待联调”，不是“不支持”。

## 3. 建议实现边界

以下是技术建议，不替代产品定案，不在本轮落地代码。

- 结果数据层：区分不可变结果、候选批次、定稿引用、历史切换记录、配置草稿与执行快照。结果可复用同一资产，但不能混用结果编号和资产编号。
- 当前展示层：可以保留 asset/content 作为当前定稿的兼容投影，由统一逻辑派生，避免旧工具入口与候选各写一份内容。
- 输入解析层：统一参考展示、请求内容和模型数量校验；只读取直接上游有效输出及显式参考。
- 任务层：先冻结执行快照，再发送；回调按请求身份追加结果，是否切换定稿由已确认规则决定。
- 持久化层：所有结果编号和资产引用必须被校验及恢复；旧单素材文档迁移为既有结果，不伪造生成记录。
- 界面层：候选查看与历史查看可以共享预览组件，但概念及操作不能混淆。具体容器需设计确认。

## 6. 产品确认顺序

每次只确认一个核心决策，确认后更新需求文档，不把推荐方案自动转成已确认。

1. 已确认：文本、视频、单图生成成功自动覆盖当前输出；多图新批次默认第一张有效图片，用户可在本批次内改选。再创作成功由最新批次取代上次选择，旧批次与选择记录进入历史，不删除旧结果。
2. 候选展开和历史记录模块的设计形式、尺寸及分组边界。
3. 已确认：服务端生成任务 ID 返回前禁止操作（当前节点还是整个画布待确认）；取得 ID 后允许改提示词、参数和当前节点连线，仅影响后续执行。生成动画期间不允许替换或切换定稿。全部失败恢复旧结果并提示失败；部分成功保留成功候选、默认第一张有效图片并提示成功数量。
4. 上传多文件、素材节点身份、缺少有效上游时的执行策略。
5. 分享范围、复制历史范围及历史容量。

文档一致性问题：需求方后续要求“新结果覆盖旧结果必须新增历史记录模块”，但主需求第 11 节仍列“上传旧定稿是否保留”。实施前应统一这一表述，不能据此自行允许上传丢弃旧结果。生成期间禁止替换和切换定稿，不再采用允许操作后比较优先级的方案。

新增技术核查与测试：确认各生成接口真实任务 ID 的返回时机，不能用本地请求编号解锁。测试提交前锁定、受理后编辑、提交失败解锁、修改连线不改已发请求、完成后不回写旧草稿／旧连线、历史入口不能绕过定稿锁定。同节点仍禁止重复提交。
