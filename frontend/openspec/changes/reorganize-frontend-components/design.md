## Context

miioo 是 React 19 + Vite 8 + Tailwind CSS v4 的深色主题应用。当前页面和组件目录已经包含一定的业务拆分，但复杂页面仍把入口、局部组件、请求、状态和交互集中在单文件中：`StoryboardPage.jsx` 约 7187 行、`CreationPage.jsx` 约 7013 行、`AssetsPage.jsx` 约 4177 行、`SubjectPage.jsx` 约 4004 行。代码盘点还发现约 242 个原生 `<button>`、约 678 个 `onClick`、约 15 个 Modal 命名文件，且多个页面内部定义了大量局部组件。

现有 Markdown 已有视觉 Token、Button 组件和结构索引规则，但主要依赖人工遵守。当前已经提供 `npm run check:architecture`，用于检查命名、基础 UI 反向依赖和历史页面规模告警；更细的页面尺寸、导入图和结构检查仍需在阻断级别与豁免方式明确后再增加。重构必须以“结构变化、行为不变”为前提，不能把组件抽离与接口协议、视觉设计或业务流程变更混在一起。

## Goals / Non-Goals

**Goals:**

- 建立清晰的基础 UI、反馈/遮罩、业务动作和业务域组件分层。
- 让页面入口主要负责页面级状态编排和区块组合，逐步降低超长文件复杂度。
- 以 Button 为第一批基础组件，统一变体、尺寸、图标、禁用和加载语义，并保持现有视觉规范。
- 建立从盘点、样板页、分阶段迁移到验收的可重复流程。
- 将页面命名、基础依赖方向和历史页面规模提示接入 npm 检查命令；页面 300 行、组件 250/400 行、Hook 300 行和函数 50 行先作为警告线，不直接阻断。
- 保留新旧实现并存期间的安全迁移能力，保证每一步都可单独构建和审查。

**Non-Goals:**

- 不修改后端 API、数据结构、路由协议或业务规则。
- 不在第一阶段引入大型状态管理、组件库或新的运行时依赖。
- 不强制把所有按钮合并为一个巨型组件，也不追求所有局部组件全局复用。
- 不一次性重写 `CreationPage` 或 `StoryboardPage`。
- 不以降低行数为唯一目标；可读性、边界和行为稳定优先。

## Decisions

### 1. 按复用范围分层，而不是按视觉元素全局化

- `src/components/ui/` 只放无业务知识的基础组件，例如 `Button`、`IconButton`、`Input`、`Select`。
- `src/components/feedback/` 和 `src/components/overlay/` 放跨业务反馈与遮罩组件，例如 `Toast`、`ConfirmDialog`、`Modal`。
- `src/components/actions/` 放跨页面且带业务语义的动作组件，例如保存、删除、生成、上传。
- `src/components/<domain>/` 放只在某业务域稳定复用的组件。
- 页面目录负责入口和页面专属编排；页面内允许临时局部组件，但迁移任务不得继续扩大重复实现。

替代方案：把所有组件放入一个扁平的 `components/` 目录。放弃原因：目前已有大量 Modal、admin 和业务组件，扁平目录无法表达依赖边界，长期仍会形成大文件。

### 2. Button 采用基础组件族 + 业务动作组件

基础 `Button` 负责视觉和通用交互，不引用 API、Store 或页面；`IconButton`、`TextButton`、`ButtonGroup` 负责稳定的结构变体。涉及权限、请求、Toast 或业务条件的按钮放在 `actions/` 或业务域目录。

替代方案：只创建一个含几十个布尔属性的超级 Button。放弃原因：不同业务语义会让基础组件耦合接口和页面状态，最终比原代码更难维护。

### 3. 先做样板页，再按风险迁移

迁移顺序采用：`ProjectList`/`GlobalSettings` 样板页 → `ScriptPage` → `SubjectPage` → `AssetsPage` → `CreationPage` → `StoryboardPage`。每个页面先盘点再拆分，首个迁移只做结构变化，不同时改接口和业务行为。

### 4. 检查优先使用无依赖脚本，后续再增强 ESLint

第一阶段使用 Node 内置模块写 `scripts/check-architecture.mjs`，检查页面规模、命名、目录层级和明显的反向依赖，并通过 `npm run check:architecture` 暴露。这样不需要增加运行时依赖，也能在现有 CI/本地环境执行。更细的 import 图和结构检查待规则稳定、阻断级别与豁免方式明确后再接入 ESLint 插件或专用工具。

### 5. 文档分为规则、架构和迁移记录

- `AGENTS.md`/`CLAUDE.md` 只保留短而硬的协作规则和入口。
- `docs/architecture/` 记录目录分层、页面职责、状态边界和导入规则。
- `docs/refactor/` 记录盘点、迁移顺序、验收标准和已完成页面。
- OpenSpec 变更目录记录本次重构的契约、技术决策和任务状态。

## Risks / Trade-offs

- [迁移期间新旧按钮并存] → 为每个迁移页面保留行为对照清单，禁止新增旧样式变体；完成后用搜索检查旧实现残留。
- [过度抽象导致组件 API 复杂] → 只有至少两处稳定复用或明确的设计系统契约才进入 `ui/`；一次只抽一个最小接口。
- [大页面拆分引入状态闭包或副作用回归] → 先提取纯展示区块，再提取动作 Hook；每个阶段执行构建、Lint 和人工关键流程验收。
- [行数检查误伤复杂但合理的文件] → 先作为告警并允许显式豁免，待样板页验证阈值后再升级为阻断。
- [旧 Markdown 与新规则冲突] → 每完成一个阶段使用文档同步流程，合并重复规则并删除过期计划，不继续追加互相矛盾的规范。

## Migration Plan

1. 完成本次盘点文档、组件架构文档和自动检查脚本设计。
2. 建立基础目录、导出入口和 Button 组件契约，不迁移业务页面。
3. 以 `ProjectList` 为首个样板页，以 `GlobalSettings` 为第二个局部样板，完成按钮和局部区块迁移。
4. 通过构建、Lint、架构检查和关键交互回归后，按风险顺序逐页迁移。
5. 每个页面单独提交，避免跨页面大批量改动；出现问题时只修正当前迁移，不回滚其他已有工作。
6. 阶段完成后同步 `AGENTS.md`、`CLAUDE.md`、`PROJECT.md` 和 `docs/`，再归档 OpenSpec 变更。
