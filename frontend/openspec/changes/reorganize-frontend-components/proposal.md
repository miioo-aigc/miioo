## Why

miioo 当前多个业务页面将页面入口、局部组件、交互逻辑、接口调用和样式集中在单文件中，`StoryboardPage.jsx`、`CreationPage.jsx` 等文件已超过 7000 行，导致复用困难、修改风险高、规范难以执行。现在需要先建立可验证的组件分层和迁移方法，再按页面逐步拆分，确保结构变清晰的同时保持现有业务行为和视觉表现不变。

## What Changes

- 建立 `ui`、`feedback`、`overlay`、`actions` 和业务域组件的分层约定。
- 盘点现有按钮、弹窗、局部组件、重复交互和超长页面，形成可持续更新的组件资产清单。
- 建立基础按钮组件族，优先覆盖现有 Button 设计规范中的变体、尺寸、图标、禁用和加载状态。
- 以一个低风险页面作为样板，验证“页面入口只负责编排、组件负责局部视图、Hook 负责页面状态”的迁移方式。
- 按风险从低到高逐步整理项目列表、全局设定、剧本、主体、资产库、创作和分镜页面。
- 增加页面规模、目录边界、命名和依赖方向的自动检查，将关键约束从人工文档转为可执行规则。
- 重写项目架构文档，使规则与代码目录、命令和迁移流程保持一致。
- 本次重构不改变后端接口协议、业务数据结构、页面视觉设计和用户流程；所有行为变化必须另立变更。

## Capabilities

### New Capabilities

- `component-architecture`: 定义组件分层、页面职责、复用边界和依赖方向。
- `ui-button-system`: 定义可复用按钮组件族及其视觉、交互和可访问性契约。
- `architecture-checks`: 定义页面规模、目录依赖、命名和结构检查命令。
- `refactor-migration-process`: 定义按页面渐进迁移、行为保持和验收的流程。

## Impact

- 主要影响 `src/pages/`、`src/components/`、后续新增的 `src/hooks/` 和架构检查脚本。
- 需要补充 `docs/architecture/`、`docs/refactor/` 和 OpenSpec 变更文档。
- 可能新增基础 UI 组件文件和测试/演示入口，但不新增运行时依赖作为第一阶段前置条件。
- 现有页面将分阶段迁移，迁移期间允许新旧组件并存，但禁止扩大旧的页面内重复实现。
