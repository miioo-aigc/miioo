# 主体与资产库删除关系修复方案

## 问题现象

本次涉及两个相互关联的删除问题。

### 问题一：主体页面删除主体后，资产库仍保留主体资产

复现步骤：

1. 在主体页面手动新增角色 A。
2. 从资产库选择或上传一张定稿图，并将其绑定到角色 A。
3. 查看资产库，确认项目资产中已经出现角色 A 的资产卡片。
4. 从主体页面删除角色 A。

实际结果：

- 主体页面中的角色 A 已成功删除。
- 资产库中角色 A 的主体资产仍然存在，形成主体已删除、资产仍可见的孤立卡片。

### 问题二：资产库删除主体资产时误删创作资产本体

复现步骤：

1. 在主体页面为角色 A 上传或生成一张创作资产，并将其绑定到角色 A。
2. 在资产库中打开角色 A 的主体资产卡片。
3. 删除该主体资产，或删除整个主体卡片。

实际结果：

- 创作资产与角色 A 的关联被删除的同时，创作资产本体也被移入回收站或删除。
- 创作资产库中原本仍应保留的图片无法继续使用。

## 根本原因

1. **主体删除只删除主体记录，没有先处理项目资产关系**

   原有 `apiDeleteSubject()` 直接调用主体删除接口。主体删除后，资产库中的资产记录仍保留原来的 `subject_id`，资产聚合逻辑继续把这些资产展示为主体卡片，因此产生残留资产。

2. **资产删除统一按“删除资产本体”处理，没有区分资产来源**

   资产库原有的单张删除、主体卡片删除和批量删除都调用删除接口，将选中的资产 ID直接发送到 `/api/assets/batch-delete` 或单项删除接口。该行为适用于主体自有资产，但不适用于从创作页上传或生成后再绑定到主体的创作资产。

3. **主体资产卡片聚合时丢失来源信息**

   主体卡片是由多条资产记录聚合而成。旧的聚合结果没有完整保留 `project_id`、`source` 和 `metadata_json`，删除时无法可靠判断当前图片究竟是主体自有资产还是创作资产。

4. **创作资产的正确操作是解除引用，而不是删除本体**

   创作资产被主体页面或资产库主体卡片引用时，`subject_id`只是关联字段。删除主体引用应更新资产记录为 `{ subject_id: null }`，不能调用移入回收站的批量删除接口。

5. **旧返回结构和分页结果可能缺少来源字段**

   仅依赖当前项目资产列表中的 `source` 字段并不可靠。部分历史数据可能没有来源字段，或在主体绑定后带有 `project_id`但仍属于创作资产，因此需要额外查询 `scope=creation` 的资产 ID作为兜底识别。

## 正确行为

### 从主体页面删除主体

1. 删除主体前，先按当前 `project_id` 分页读取项目资产。
2. 筛选 `subject_id` 等于当前主体 ID的全部资产。
3. 对主体自有资产调用批量删除接口，正常移入回收站。
4. 对创作资产只调用资产更新接口，将 `subject_id` 更新为 `null`，保留创作资产本体。
5. 上述资产关系处理成功后，再调用主体删除接口。
6. 删除完成后刷新主体列表和项目资产缓存，资产库不再展示已删除主体的卡片。

### 从资产库删除主体资产

1. 单张删除、整张主体卡片删除和批量删除统一进入资产移除逻辑。
2. 主体自有资产继续移入回收站。
3. 创作资产只解除与主体的 `subject_id` 引用，不删除、不移入回收站、不影响创作资产库。
4. 删除主体卡片后，同时清理当前页面的聚合数据和分页原始数据，避免翻页或触底加载时重新出现空卡片。
5. 删除创作资产的主体引用后，刷新项目资产相关缓存，使该资产从主体卡片中消失，但仍能在创作资产库中查询到。

## 修改位置

### `src/api/assets.js`

- 新增 `apiRemoveAssets()`，统一处理单张、主体卡片和批量资产删除。
- 通过 `source`、`source_type`、`metadata_json`等字段识别创作资产。
- 额外调用 `GET /api/assets?scope=creation`，用创作资产 ID集合兜底识别来源字段缺失的创作资产。
- 主体自有资产调用 `/api/assets/batch-delete`移入回收站。
- 创作资产调用 `PATCH /api/assets/{asset_id}`，请求体为 `{ subject_id: null }`，只解除主体引用。
- 新增 `apiDeleteSubjectAssets()`，在主体删除前分页收集当前主体关联的项目资产，并复用统一删除逻辑。
- `normalizeAsset()`和主体聚合结果保留 `project_id`、`source`、`metadata_json`，避免聚合时丢失删除所需的来源信息。

### `src/api/subject.js`

- `apiDeleteSubject()`在删除主体记录前调用 `apiDeleteSubjectAssets(projectId, subjectId)`。
- 只有主体关联资产处理成功后，才继续调用主体删除接口。
- 保留原有主体及项目资产缓存失效逻辑，确保页面能同步最新数据。

### `src/pages/AssetsPage.jsx`

- `ProjectAssetsPanel`的单张删除、整张主体卡片删除和批量删除全部改用 `apiRemoveAssets()`。
- 删除时传入完整资产记录，供 API 层判断创作资产来源。
- 删除主体卡片后从 `assetsMap`移除卡片，并从分页 `rawList`中移除对应图片，避免出现可点击空卡片或重复加载。
- 更新文件顶部结构索引，补充删除函数和副作用的位置说明。

## 边界条件

- **主体自有资产**：没有创作来源标记的主体资产，按原有规则移入回收站。
- **创作资产**：无论是主体页面上传、主体页面生成，还是其他创作流程产生后绑定到主体，只解除 `subject_id`引用，保留创作资产本体。
- **来源字段缺失**：优先读取 `source`、`source_type`和 `metadata_json`；如果资产记录缺少这些字段，则通过 `scope=creation`返回的资产 ID集合兜底判断。
- **同一主体混合资产**：同一主体下同时存在主体自有资产和创作资产时，逐条分类处理，不能把整张主体卡片内的所有资产统一删除。
- **单张删除**：删除主体卡片中的一张创作资产时，只解除这一张资产的主体引用，其他图片和创作资产不受影响。
- **整张卡片或批量删除**：对选中的全部资产逐条分类；主体自有资产移入回收站，创作资产只解除引用。
- **分页数据**：删除当前已加载的主体卡片后，必须同步清理分页原始数据，防止后续加载重新聚合出已删除主体。
- **无关联资产的主体**：主体没有任何项目资产时，直接删除主体，不发起无意义的资产删除请求。
- **资产处理失败**：资产关系处理失败时终止主体删除，避免主体删除后无法再定位待处理资产；页面保留原状态并提示错误。
- **接口重复调用**：统一删除函数对主体自有资产和创作资产分别调用对应接口，避免同一资产同时进入删除和解除引用流程。

## 回归测试

### 测试一：主体页面删除主体及其资产

1. 在主体页面新增角色 A。
2. 从资产库选择或上传一张定稿图，并绑定到角色 A。
3. 查看资产库，确认角色 A 的主体资产卡片出现。
4. 从主体页面删除角色 A。
5. 确认主体页面不再显示角色 A。
6. 确认项目资产库不再显示角色 A 的主体卡片。
7. 确认如果该资产属于创作资产，创作资产库中仍能查询到该资产，且其 `subject_id`已变为 `null`。
8. 确认如果该资产属于主体自有资产，资产已进入回收站。

### 测试二：资产库删除主体资产

1. 为角色 A 准备至少一张主体自有资产和一张创作资产，并将两者都绑定到角色 A。
2. 在资产库中单张删除创作资产。
3. 确认该图片从角色 A 的主体卡片中消失，但创作资产库中仍保留。
4. 单张删除主体自有资产，确认其进入回收站。
5. 再执行整张主体卡片删除或批量删除，确认两类资产仍按来源分别处理。
6. 切换资产分类、翻页或触底加载，确认已删除主体卡片不会重新出现。

### 测试三：异常和历史数据

1. 使用缺少 `source`字段但能在 `scope=creation`查询到的历史创作资产执行删除，确认只解除引用。
2. 使用没有关联资产的主体执行删除，确认主体可以正常删除。
3. 模拟资产删除接口失败，确认主体删除不会继续执行，页面不会提前移除未成功删除的数据。
4. 确认单张删除、整张删除和批量删除不会重复处理同一个资产。
